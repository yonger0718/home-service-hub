# Statement reconciliation (對帳) — design

Status: **v4**, final after three Multica review rounds on AGENT-83 (rounds 1/1.1 → v2, round 2 → v3, round 3 → v4). §15 is the cumulative answer map; §16 lists what is carried into the implementation plan as acceptance criteria rather than re-specified here. Owner decisions are **[owner]**; defaults **[default]**; open owner items are in §14. Wherever this document says "as v2", it means the text of commit `eef3b31aa517368c34f57dfb1c9dd785e86ac1fa`.

## 1. Problem

The reminder centre's 信用卡帳單 only says how much to pay; nothing checks the ledger against what the bank billed. The owner's Hermes mail automation already lands every card and bank e-statement in Google Drive:

| Drive path (under `財務對帳單/`) | content (2026-10-09) |
|---|---|
| `銀行/信用卡/<issuer>/` | 14 card folders, emailed e-statements, `YYYY-MM_<issuer>_…pdf` |
| `銀行/銀行帳戶/<bank>/` | 12 bank folders, emailed e-statements |
| `手動下載/國泰世華/` | 12 monthly Cathay 綜合月結單, `YYMM.pdf`, owner-downloaded |
| `投資/`, `電子發票/` | out of scope |

496 bank PDFs + 12 manual. Every PDF is password-protected. A read-only spike (one or two files per folder) unlocked every folder with the owner's password rules and found a text layer in every file, so **v1 has no OCR and no vision path**. Two folders use uppercase `.PDF`. 台新 changed its password rule in 2024-12.

Goals, in priority order:
1. Per statement period: every statement line is matched to ledger rows, explained (bank fee, interest, reward, deferred) or an open case; same in reverse.
2. The ledger converges to the statement only through explicit, validated, reversible, audited actions. Nothing writes money without the owner's grant.
3. Unattended for new statements; idempotent over history.
4. The triage brain is replaceable.

Non-goals (v1): bank logins/scraping **[owner]**, OCR/vision, investment and e-invoice files, chat-based approval, historical ledger repair.

## 2. Shape

| Layer | Runs in | Handles |
|---|---|---|
| Rules | API process, `reconciliation_service` (pure, deterministic) | eligibility gates, competing representations compared globally per line, monetary conservation, bank-only lines, deferral, cross-account hints; never resolves ambiguity |
| Model as a function | sandboxed, tool-less parser child of the ingest worker | masked statement text → `StatementParse` JSON |
| Agent triage | Hermes skill, `read,propose` token | proposals on open cases |
| Apply | API process, owner tap or policy engine under owner grants | one transaction per action, event-identity idempotency, audit, operation-specific inverse |

## 4. Data model (Alembic `statement_tables`)

Types follow the ledger: money `Numeric(20, 4)`, ids `Integer`, dates `date`, timestamps `timestamptz`. New enums get their own types. The PostgreSQL enum `entry_source` gains `statement` (`ALTER TYPE entry_source ADD VALUE`, committed in its own migration step before any use). Downgrade refuses while any `ledger_entry.source='statement'`, coverage, action or audit row exists. The operator confirms the live head with `alembic current`; the migration test suite runs upgrade/downgrade on a populated database, including trigger/FK ordering so `ON DELETE SET NULL` can never leave an active claim pointing at a deleted row.

### 4.1 `ingest_run` (B1, S1)
`id, trigger ('timer'|'owner_cli'|'enqueue'), principal (token label; for timer/CLI 'worker' plus `initiator_hint` unix user, unauthenticated), mode ('live'|'backfill'), status ('queued'|'claimed'|'running'|'done'|'failed'|'expired'), claimed_by, lease_token, lease_expires_at, attempt, parser_version, rules_version, policy_config_sha256, mapping_version, credential_version, requested_at, started_at, finished_at, summary JSONB`.
Protocol: enqueue (`POST /statements/ingest/run`, scope `enqueue`) inserts `queued` or returns the existing non-terminal run (coalesced; the request is appended to `summary.coalesced[]`). **No file handoff**: the worker (timer tick every 5 min, and its daily full run) polls `GET /statements/ingest-runs?status=queued` with scope `ingest`, then `POST …/{id}/claim`, which atomically moves `queued → claimed` (`UPDATE … WHERE status='queued'`), sets a 30-minute lease and returns a `lease_token`. Every submission carries the run id and lease token; the API accepts it only if the run is `claimed`/`running`, the token matches and the lease is live (else 409). Leases are renewed by the worker every 5 minutes; an expired lease moves the run to `expired`, a new claim gets a new token and increments `attempt`; late submissions with the old token are refused. Restart recovery: a worker finding its own `claimed`/`running` run with a live lease resumes it; otherwise it waits for expiry. Timer/CLI runs are created by the worker itself. Tests: two enqueues coalesce, crash before claim, crash after claim and reclaim after expiry, late submission with a stale token refused, submission to a `done` run refused.

### 4.2 `statement_file` and `statement_source` (A11, C9, S2)
`statement_file`: `id, sha256 (unique), size, kind, account_id (nullable), object_key, status, failure, has_text_layer, text_chars, pages, credential_version, mapping_version, parser_version, attempts, next_retry_at, first_seen_at, parsed_at, run_id`.
`statement_source`: `id, file_id, root ('mail'|'manual'), drive_file_id, drive_path, drive_md5, drive_size, path_history JSONB, first_seen_at, last_seen_at, removed_at, superseded_by_source_id`. Many sources per file; many files per path over time; rename appends to `path_history`; Drive deletion sets `removed_at` only after a **complete** listing (a listing error aborts the run without marking anything removed).
Retry triggers and singleton: as v2 (`transient` backoff, `credential_version`/`mapping_version`/`parser_version` changes; `flock`).

### 4.3 `account_statement` — as v3 (`mode` immutable, `conflict_open`, `needs_recheck`, `swept_through_event_id` added, see §4.6).

### 4.4 `statement_revision`, `statement_line`, `statement_event` (A2, C2)
`statement_revision`: as v3, immutable.
`statement_line`: **immutable rows per revision**, as v3 (`canonical_key`, `logical_key`, `flow_amount`, …), plus `event_id`.
`statement_event`: the **persistent financial-event identity** of a statement line across revisions: `id, statement_id, first_revision_id, first_line_id, current_line_id (nullable while unpaired), status ('live'|'retired'|'quarantined'), created_at`. Created for every line of a statement's first revision; on later revisions lines are paired to events (§5.7). All coverage, cases, proposals, explanations, dismissals and action effects reference the `event_id`, never a line id alone. Unique active effect: `reconciliation_action` has a partial unique index on `(event_id, action, effect_slot) WHERE status='applied'` (`effect_slot` = `'create'` for creations, `'fee'` for the fee child, `'match'` otherwise), so a second creation/fee for the same event is refused at the database, not only by a lookup.

### 4.5 `line_lineage` (C2)
`id, event_id, old_line_id, new_line_id, equivalence ('identical'|'normalised'|'changed'|'unpaired'), transferred bool, created_at`. `normalised` = everything equal after the merchant normaliser (token set identical, differences only in whitespace/punctuation/case); a merchant change from A to B is `changed`. Transfer rules in §5.7.

### 4.6 `statement_coverage` and the dirty protocol (A3, A6, C3)
`statement_coverage`: `id, statement_id, event_id, line_id, entry_id (nullable), group_id (nullable), role, snapshot JSONB, match_kind, match_rule, status ('active'|'stale'), stale_reason, run_id, created_at`. Unique `(entry_id) WHERE status='active' AND entry_id IS NOT NULL`. Conservation invariant asserted before commit (as v3). FKs `ON DELETE SET NULL` with snapshots.

**Dirty events** (`coverage_dirty`): `id (bigserial, the generation), kind ('entry'|'group'|'account'), row_id, op ('insert'|'update'|'delete'), old JSONB, new JSONB, action_id (nullable), happened_at`. Row-level `AFTER` triggers on `ledger_entry` (all persisted columns that matter: `account_id, amount, currency, original_amount, original_currency, fx_rate, entry_date, posted_date, kind, name, merchant, group_id, parent_entry_id, transfer_group_id, refunds_entry_id, settles_entry_id, is_settlement, reward_source_entry_id, reward_rule_id, source, import_run_id`), `entry_group` (all columns), `account` (`opening_balance, currency, combined_account_id, closing_day, due_rule, due_value, is_credit, is_archived`). Triggers are append-only (never mutate their source tables, so no recursion), use null-safe `IS DISTINCT FROM` comparisons (no event for no-op updates), and record **both OLD and NEW** rows so every affected population can be derived: old and new account, old and new period (by `posted_date`/`entry_date`), old and new group/parent/combined parent, old and new link targets. `action_id` is filled from a transaction-local setting (`SET LOCAL app.reconciliation_action_id`) that only the apply path sets, so self-generated events are attributable.

**Sweep protocol**: `sweep(statement)` runs inside the statement's transaction (lock order §7.4), reads events with `id > statement.swept_through_event_id` whose old or new population touches the statement (account ∈ participating set now or before, and date within the period ± window, or a referenced row has active coverage/explanation in this statement), applies them (stale coverage with the line's claim released as a whole, cases reopened/created in live mode, summary-only in historical mode **but coverage is still released**, `needs_recheck` for account-level/insert events), skips events whose `action_id` belongs to an action applied on this statement, then advances `swept_through_event_id` to the highest id it has seen. Events are never deleted by the sweep (a retention job removes events older than every statement's watermark). Writers never lock statements, so there is no inversion; a writer committing after a sweep produces a higher event id that the next sweep sees.
Reads: every statement GET returns `stale_events_pending = exists(event id > watermark touching this statement)`; the UI shows 需重新同步 and the detail is computed from stored rows (no mutation on GET). Confirm and apply always sweep first under the statement lock, so a confirmation can never be based on an unswept state.
Service hooks (`coverage.touch`) remain as the immediate path for UX; they only insert events through the same table.
Tests: every write path listed in round 2/3 (bulk delete, repost/reopen, settlement relink, child replacement, member detachment, reward unlink, account config edit, combined-child relink both parents, cross-period move of an uncovered row, delete of an unmatched row in a reconciled period, insert into a reconciled period), barrier tests edit/insert/delete-vs-confirm, historical release of a stale claim, self-generated events not reopening fresh coverage, trigger amplification on an import-sized batch.

### 4.9 `reconciliation_action` + audit (A8, C2, C6)

Snapshot scope (acceptance criterion, §16): every persisted field of each touched entry and group, the complete child/member id sets, and incoming dependencies (refund/settlement/reward links, schedule instance membership). Compare-and-write happens after the §7.4 locks are held and the locks are retained through commit; relationship writers (child insert, member add/relink) already lock the parent entry/group first, which this design relies on and the tests verify (concurrent child insert during apply must either serialise or be detected).

## 5. Ingest worker

### 5.1 Acquisition (A11, C9)
List with `rclone lsjson --hash --recursive` (`ID, Path, Hashes.md5, Size, ModTime`), case-insensitive `.pdf`. For each `(drive_file_id, md5)` not yet in `statement_source`: download with `rclone copyto` by **file id** (`--drive-root-folder-id`/id addressing, not the path) into a private staging dir; verify size and md5 of the downloaded bytes against the listing (mismatch → re-list once, then skip with `transient`); compute sha256; publish atomically into `inbox/by-sha/<sha256>.pdf` (`rename` onto a temp name, never overwriting an existing object with different bytes — a collision is a hard failure); only then register file and source via the API and put to MinIO (idempotent by sha256). Failure matrix: local publish ok + MinIO fail → retry MinIO next run (file row `transient`); MinIO ok + API fail → re-register next run (idempotent); any listing error → abort before `removed_at` logic. Tests: source replaced between list and copy, crash at each boundary, incomplete listing.

### 5.2 Account mapping — as v2. 5.3 Unlock — as v2. 5.4 Probe/extract/mask — as v3 (bounds, masking patterns, canary).

### 5.5 Parse (D1, D3, B2, C7, C8)
Regex parsers first when registered. Fallback: the parser child, CLI pinned to **2.1.295** (refused otherwise until the pin is bumped after a passing gate).
```
bwrap --unshare-all --share-net --die-with-parent --new-session --cap-drop ALL \
  --ro-bind /usr /usr --ro-bind /lib /lib --ro-bind /lib64 /lib64 --ro-bind <node> /node \
  --ro-bind /var/lib/home-hub-parser/claude /cfg --bind /var/lib/home-hub-parser/claude/.credentials.json /cfg/.credentials.json \
  --tmpfs /tmp --tmpfs /work --chdir /work \
  --setenv HOME /tmp --setenv CLAUDE_CONFIG_DIR /cfg --setenv PATH /node/bin:/usr/bin \
  -- claude -p --safe-mode --tools "" --disallowedTools "mcp__*" --strict-mcp-config --mcp-config '{"mcpServers":{}}' \
     --permission-prompts none --no-session-persistence --max-turns 1 \
     --output-format stream-json --json-schema "$(cat schema.json)" --model <pinned model id> "<fixed instruction>"
```
Writable surfaces, stated exactly: `/tmp` and `/work` (tmpfs, discarded), `/cfg/.credentials.json` (OAuth refresh). Everything else read-only or absent (`/etc` absent: no local managed settings, no DNS config → the sandbox gets a minimal `/etc/resolv.conf` and `/etc/ssl` bound read-only, which the gate verifies). The worker consumes the **stream** (`stream-json`): any `tool_use`, hook, or subagent event → the run is failed and parsing is disabled (`failed/sandbox`) until an operator re-runs the gate; the final result's `structured_output` is validated with pydantic `StatementParse` (as v3). Bounds: stdin ≤ 400 KB, stdout and stderr each capped at 2 MB while streaming (truncation = failure), 120 s per attempt, 3 attempts, `max_turns` hit = failure, process group killed and reaped on expiry. **Gate** (at worker start, after any CLI/config/pin change, and daily): a canary prompt run under the same command must yield exactly one assistant turn, zero tool/hook/subagent events, a schema-valid output, no files outside the stated writable surfaces (checked by a post-run diff of the read-only mounts' mtimes and a `find` over `/cfg`), and no child processes other than the CLI's own (bwrap `--new-session`, `/proc` inspection from the worker). Server-managed policy cannot be inspected offline; the operator's evidence is the account-level confirmation in §3. If the gate cannot pass with the pinned command, parsing stays off; the gate does not "pass by omission".

### 5.6 Submission and server-side guardrails — as v3 (API derives `flow_amount`, mode, mapping, guardrails; never trusts submitted flags).

### 5.7 Re-parse, events and lineage (C2)
A new revision pairs its lines to the statement's `statement_event` rows: first by `logical_key` with identical `canonical_key` (`identical`), then by `logical_key` with `normalised` equivalence, in print order among identical twins. Pairs with any other difference are `changed`; events with no pair are `unpaired`; new lines without an event get a new event. Transfer: `identical` → coverage, explanations, dismissals and pending proposals carry over; `normalised` → coverage transfers, pending proposals superseded, line flagged 文字已變更; `changed`/`unpaired` → the event is **quarantined** when it has any applied action or active coverage (its coverage released, a `parse_review` case opened, nothing automatic), else simply retired. A quarantined event's effects remain unique (§4.4): a replacement line (new event) cannot create/fee again until the owner resolves the quarantine, because the resolution either re-links the new line to the old event (keeping its effects) or explicitly reverts the old effects first. Twin-count changes and header changes → `parse_review`, no transfers. Reconciled statement + new revision → `conflict_open` (as v3). Fixtures: corrected date/amount after an applied create, two genuinely identical purchases, same-count reordered distinct twins, merchant change with an old applied effect.

### 5.8 Modes (A9, C7)
`live`, `historical`, `backfill`: as v3. `verify` is now two steps because verify cannot decrypt: (1) the worker, as `homehub-worker`, runs `export-masked --for-verify` (local only: unlock + extract + mask, writing masked text snapshots by sha256 into `/var/lib/home-hub-verify/masked/`, no API or MinIO calls); (2) `homehub-verify` runs the verify runner over those snapshots: parser child (its own read-only login mount), pure matching against a read-only snapshot through `accounting_ro`, report into `/var/lib/home-hub-verify/reports/`. Neither step can write application state; tested with policies enabled.

### 7.2 Actions (as v3, with C4/C6/C8 changes)
- `attach_fee`: params `entry_id, fee_line_id?`; the purchase line is bound from the case's event (bundled) or `fee_line_id` must be a fee line of the same statement (separate); an action lacking that binding is rejected; `fee = residual` as v3, **and** `0 < fee ≤ 5 % × |principal|`, and the child amount must satisfy the exact conservation assertion (a quantum-tolerant residual that would break exact conservation fails with no partial effect). Tests: zero, negative, excessive, quantum-violating.
- `adjust_amount`: `fx_rate := amount / original_amount` derived from the authoritative pair (as base `resolve_fx` does), with zero checks and the ledger's precision; the prepared market rate is not stored. 
- `link_installment_plan`: `case_id, definition_id` → inserts `installment_plan_map` (owner only) and re-runs the line.
- `balance_adjustment_asof` (C4): contract = **account generation compare-and-write**, not SSI. `account.balance_generation` (bigint) is incremented by the `ledger_entry` triggers of §4.6 for the affected account(s) (old and new on moves) and by account-config triggers. The action: read `generation`, compute `delta` over `posted_date ≤ period_end` in READ COMMITTED, then take the account row lock, re-read `generation`; if unchanged insert the adjustment (the insert itself bumps the generation) and commit; if changed, roll back the whole transaction and retry from the start (fresh statement/current-revision validation) at most 3 times; on exhaustion return 409 with no action, budget or audit effect. Later edits are caught by the dirty protocol (`needs_recheck`). Tests: concurrent edit and delete of summed rows between compute and lock, double submit, exhaustion.

### 8.1 Token scopes (M9, A1, C1)
Authorization is **independent of feature mounting**. Rules:
- When `ACCOUNTING_TOKEN_SCOPES` is set, the scope dependency is enforced on every router whether or not reconciliation is enabled; unknown scope names, unknown or duplicate labels, duplicate token values and malformed maps refuse startup.
- When `ACCOUNTING_TOKEN_SCOPES` is unset ("compatibility mode"), startup refuses if `ACCOUNTING_RECONCILIATION_ENABLED=true` **or** if any configured token label is one of the restricted names (`hermes`, `worker`, or any label in `ACCOUNTING_RESTRICTED_LABELS`); compatibility mode therefore exists only for an all-legacy token set and cannot be reached while a restricted credential is configured.
- Turning the feature flag off with scopes still set keeps every restriction (the statement/reconciliation routers are simply not mounted). Test: enabled→disabled with the Hermes token against every existing mutation route stays 403.
- Scopes and the `legacy`/`ingest`/`enqueue` exclusions as v3; PR-R4 grants Hermes `read,propose` only (S2), `enqueue` later on the owner's word.

## 17. R1a implementation notes (2026-10-09, PR "R1a")
Decisions taken during implementation that refine this document:
- **Dirty triggers are gated** by `reconciliation_settings.data->>'dirty_enabled'` (one PK lookup per changed row, default off). With the flag off in production the triggers write nothing; enabling the feature = set `ACCOUNTING_RECONCILIATION_ENABLED`, configure scopes, then `PUT /settings/reconciliation {"dirty_enabled": true}` once the worker is live (§4.6, §13).
- **`balance_generation` is derived** from `coverage_dirty` (`max(id)` for the account), not an `account` column: a trigger updating `account` would take an account row lock after entry locks and invert D32 (§7.2 C4).
- **Worker-created runs**: `POST /statements/ingest-runs` (scope `ingest`) creates and claims a `timer`/`owner_cli` run in one request; `enqueue` coalesces only into `queued` runs or claimed/running runs with a live lease (§4.1).
- **Events on a revision that does not become current** are created `retired`; "live" events are those with `current_line_id IS NOT NULL` (§4.4, §5.7).
- **A `changed` pair never transfers its event**: the old event is retired (`current_line_id` NULL) and the new line gets a new event, as for an unpaired line; only `identical`/`normalised` pairs move an event. Quarantine of a `changed`/unpaired event with applied effects or active coverage arrives with effects in R1b (§5.7).
- **A guardrail-ok revision replaces a current revision whose guardrail failed** regardless of header/twin changes, and supersedes that statement's open `parse_review` cases (§4.3).
- Settings mutations require `admin`; `legacy` satisfies every scope (so the SPA token can also reach the ingest routes — the owner decides before enabling, §8.1).
- The three account statement columns are not exposed by the account API in R1a (set via the database/settings in R2).

R1b errata (2026-10-09, PR "R1b"):
- **§4.6 erratum — the sweep watermark needs a writer barrier.** `bigserial` ids are assigned at insert, not at commit, so they are not commit-ordered: a watermark advanced past a committed id N+1 could skip an in-flight N forever. The dirty triggers take `pg_advisory_xact_lock_shared(0x44495254)` before inserting; the sweep takes the same key exclusively at session level (the wait bounded by `lock_timeout`, 5 s, else `sweep_barrier_busy`), reads its cap `max(id)`, unlocks at once and scans only `id <= cap`. Preconditions: READ COMMITTED isolation and `coverage_dirty_id_seq` with CACHE 1.
- **§6.3 (v3) — installment scoring.** An installment representation with a confirmed plan inside `candidate_window_days` scores `0.90 + 0.10 × overlap`: the plan identity replaces the date term of the uniform formula. Outside the window it is never a claim; the line becomes an `installment_date_drift` case.
- **§7.4 — reconcile yields on lock conflicts.** A ledger delete locks the entry/group first and then the coverage/case rows that reference it (ON DELETE SET NULL), while reconcile writes such rows (sweep, revision transfer) before its group/entry locks. Reconcile therefore takes the group/entry locks NOWAIT and raises `reconcile_busy` (route 409; the batch records it per statement and goes on). The ingest hook runs the matcher inside a savepoint: any conflict (`reconcile_busy`, `sweep_barrier_busy`, `duplicate_claim`, conservation, import running) rolls back only the pass, sets `needs_recheck` and the revision still commits.
- **§6 — deferral links.** `deferred_to_statement_id` is filled only by the later statement's reconcile or by the batch (`fill_deferral_links`); an earlier statement's reconcile never locks or references a later statement.
- **§4.6 — gating and self-events.** The `coverage_dirty` triggers are gated by `dirty_enabled`; reconcile writes no ledger rows, so it emits no dirty events of its own.
- **§7.4 — the revision hook never waits for the dirty barrier.** Its transaction already holds the coverage/case rows the lineage transfer moved, and a writer holding the shared barrier may be waiting on them, so the hook's sweep only try-locks the barrier (`sweep_barrier_busy` at once when held); the route and batch keep the bounded 5 s wait (they hold only the statement row, which writers never lock). A residual `DeadlockDetected` inside the hook is treated like a conflict (savepoint rollback, `needs_recheck`, the ingest commits); other driver errors still fail the submission. Once the sweep holds the barrier, any failure before it reads its cap releases the lock or invalidates the connection.
- **§6.1 (v3) — currency and account gate.** Every claimable row (standalone entry, child, group member, installment instance) is on a participating account AND in the statement's currency: a combined child account may hold another currency (the account settings do not forbid it). A group with a gated-out member is partial and never admissible; a child gated out never completes its parent.
- **§6.3 (v3) — drift hint beyond the population.** The reconcile also loads the posted instance entries of the account's confirmed plans that lie outside period ± `candidate_window_days` (participating account, statement currency, not claimed elsewhere) as non-claimable entries: they only let the plan gate name the entry in an `installment_date_drift` case and are never represented, locked, claimed or reported.

### R2 implementation notes (2026-10-10, PR "R2")

The ingest worker (`services/accounting-service/worker/`, ops files in `deploy/statements/`) was built under the following rulings, recorded verbatim from the implementation plan (rev 3, after the Multica reviews AGENT-95 and AGENT-96).

1. **CLI pin bumped 2.1.295 → 2.1.296** (installed version; .295 is gone). The gate must pass before the first real parse.
2. **Structured output is a tool call.** With `--json-schema`, the CLI exposes exactly one tool, `StructuredOutput`, and the model answers by calling it: the stream is `system/init` (tools `["StructuredOutput"]`) → one `assistant` message whose content is exactly one `tool_use` named `StructuredOutput` → one `user` message (its `tool_result`) → `result` (`subtype == "success"`, `num_turns == 2`, `structured_output` set). The §5.5 gate therefore reads: tools list equals `["StructuredOutput"]`, exactly one `tool_use` and it is `StructuredOutput`, no other tool name, no `hook`/`subagent`/permission event, `num_turns == 2`. Observed with the real CLI: `system` events of subtype `thinking_tokens` and `ui_invalidate` are ignored anywhere in the stream, assistant messages with only `thinking`/`text` blocks may precede the single `tool_use` message, and the CLI's own `git` child process is allowed. Anything else → `failed/sandbox` and parsing disabled.
3. **Interim principal.** The dedicated users of §3 do not exist yet; R2 runs as `opc` with every path configurable (`STATEMENT_*` env, defaults below). The deploy notes carry the §3 checklist for the switch; the feature flag stays off in production until then, so the first real use is `export-masked` + `verify` (under ruling 11's read-only role).
4. **MinIO is optional in R2**: with `STATEMENT_MINIO_ENDPOINT` unset the put is skipped and `object_key` is still `by-sha/<sha>.pdf` (the local inbox holds the bytes). Setting the endpoint later re-uploads missing objects on the next run (the file row stays `transient` until the put succeeds).
5. **Account map reaches the worker through a new ingest-scope route** `GET /statements/account-map` (`{"account_map": …, "mapping_version": sha256-prefix}`), because the worker token holds `ingest` only and cannot read settings. `verify` reads the map from the database (read-only) or from `STATEMENT_ACCOUNT_MAP_FILE` (same key format) while the feature flag is off.
6. **Verify is in-process, read-only.** The verify runner opens one `REPEATABLE READ READ ONLY` transaction on the read-only role (ruling 11), builds candidates with `reconciliation_service.load_candidates` on a stand-in statement whose id is the existing statement's id when `(account, currency, period_end)` already exists (so its own claims are excluded like a re-reconcile) and `0` otherwise, skips matching when the guardrails fail (as `reconcile` does), and calls `matching.match`; it writes only its report. Parse results are cached by sha256 + parser version so re-runs do not re-parse.
7. **Regex parsers**: none in R2 (as spec v1); no registry either (ruling 13) — adding one later touches `pipeline.process_file` in one place.
8. **Pinned model** default `claude-sonnet-5-5` (`STATEMENT_PARSER_MODEL`); the parser version string is `claude-cli-<cli version>-<model>-<instruction sha256[:8]>-<schema sha256[:8]>`.
9. **The gate is mandatory and latched** (AGENT-95 Must 2). Every `run`, `poll`, `backfill` and `verify` calls `parser.Gate.ensure()` before the first parse: it passes when `<state_dir>/gate.json` holds a successful gate whose key (`cli_version`, `model`, `config dir mtime`, sha256 of the full argv template, sandbox flag) matches and is younger than 24 h; otherwise it runs the canary now. A violation anywhere (gate or real input) writes `<state_dir>/parser-disabled.json` (reason, time, key); while that latch exists no process parses, runs finish `failed` with `errors: ["parser_disabled"]`, and only a successful operator `python -m worker gate` removes it. `deploy/statements/gate.sh` adds the host-side evidence (mounts, processes, `/etc` and `$HOME` unreadable) and is the §16 C7 artefact.
10. **`SourceIndex` is a download cache, never the authority.** Every complete listing re-registers every listed source through `POST /statements/sources` (idempotent upsert; path history, `removed_at` reset) and re-checks the object store for every file that lacks a stored object (`store_pending` tracked locally), regardless of the index. The index only decides whether bytes must be fetched again.

Accepted scope: principal `opc`; commands `export-masked` and `verify` only; no real-data `run`/`backfill` until the §3 users exist; residual host access of `opc` acknowledged; expiry = the §3 user split. The verify transaction is `REPEATABLE READ READ ONLY`. Verify's parser child binds the login directory read-only with **no** writable credentials file (`STATEMENT_VERIFY_PARSER_CONFIG_DIR`, a copy refreshed by the operator's `gate` run); an expired token fails verify with `auth`, it never refreshes. The Linux principal stays `opc` in the interim (ruling 3), recorded as an accepted deviation from §3, not as compliance; the flag stays off and no real-data `run` happens until the §3 users exist.

13. **Narrowed contracts** (AGENT-95 Should): no regex-parser registry in R2 (ruling 7 is "none", the pipeline has a single parser); run provenance (`parser_version`, `credential_version`, `mapping_version`, `cli_version`, `model`) travels in the run's finish `summary.versions` (the `ingest_run` columns stay for R1c's API change); `backfill` prints no pre-execution live-period count (the worker cannot read accounts) — the CLI refuses without `--acknowledge-live-periods` and the summary reports `live_revisions` afterwards; the daily sweep (`POST /reconciliation/sweep`) runs at the end of every full run under its lease.

Sandbox recovery: a file failed `sandbox` becomes due again when `gate.json` is ok **and** its `checked_at` is newer than the file's `sandbox_failed_at` recorded in the worker's `RetryLog` (no parser-version change needed).

16. **Operator gate = worker gate + host checks in one Python command** (AGENT-96 Must 3): `python -m worker gate` runs, in order, the canary with the worker login, the canary with the verify login (read-only mount), and the host checks (positive control `/usr/bin/true` must exit 0 inside bwrap; `/etc/passwd` and `$HOME` must be *absent* inside the sandbox, distinguished from a broken bwrap by the positive control; the login dir diff; and process sampling **during** each canary via `ps` at t=0 then every 50 ms). The gate and every real parse enforce exactly this shape.

**Accepted interim deviation from section 3 (rulings 3 and 11).** R2 runs as `opc`, not as the dedicated users of section 3. The owner accepted this on 2026-10-10 ("ok ruling 11"). It is a deviation, not compliance. Scope: the commands `export-masked` and `verify` only, with `verify` reading through the `accounting_ro` role (`SELECT` only, `default_transaction_read_only = on`); no real-data `run` or `backfill`, and the reconciliation feature flag stays off, until the section 3 users exist; the residual host access of `opc` (it can read the worker's files and the parser login) is acknowledged. Expiry: the section 3 user split (checklist in `deploy/statements/README.md`).

**Implementation rulings taken during Tasks 2 to 8.**
- **Masking refinement (section 5.4).** Digit runs mask when they are at least 6 contiguous digits, or at least 2 groups of at least 3 digits separated by a single space or dash with at least 8 digits in total (cards 4-4-4-4, accounts 3-3-3-3 and 3-3-4 still mask; `30 2026`, `000 2026`, slash and dash dates and comma amounts never do). Phones: Taiwan mobile `09xx[- ]?xxx[- ]?xxx` and `+886` forms; a landline only with parentheses or dashes. Compact dates: an exactly 8-digit token that parses as a valid `YYYYMMDD` date in 1990..2039 is exempt from the digit-run rule (bank statements print compact dates; an 8-digit account number is rare in Taiwan). Holder names shorter than 2 characters are ignored. Over-masking of merchants by substring is accepted (privacy-safe).
- **Password grammar.** A literal `+` in a password value is unsupported: the grammar splits on `+` to join parts. An empty environment value means the default; the password file is read once per load and a UTF-8 BOM is stripped so the first identity line is not lost.
- **Account-map keys (an R1a validator fix).** The R1a `_check_account_map` required three path parts, so the manual-root key `manual/<folder>` could never be stored. Valid keys are now `mail/<folder>/<sub>` (3 parts) and `manual/<folder>` (2 parts); others are rejected. The absent settings row reads as version 1, matching the inserted row.
- **Containment and aborts.** A per-file failure is contained as `failed` or `transient` and the run goes on; only `LeaseLost`, transport errors and an `auth` failure abort the run. A parser `exit` (non-zero CLI exit, e.g. after a rate limit or an outage) is `transient`, never `failed/parse` at the current parser version. A resume discards `run.json` only on 404 or 409; a 5xx keeps it and aborts with `resume_unavailable`. The CLI exits 0 for a `done` run with transient codes and 1 only for `failed` or `aborted` runs.
- **Store confirmation.** An object-store confirmation is keyed by `host:port/bucket`; the `NullStore` never confirms, so enabling MinIO later uploads every object that lacks one. A missing bucket (`NoSuchBucket`) is a configuration error, not an absent object.
- **Gate evidence 2026-10-10:** both logins `num_turns 2`, tools `['StructuredOutput']`, host checks all true, processes_seen `['bwrap','claude']` (sampled from t=0 on both mounts: `['bwrap','claude','sh']`, the CLI's own `sh -c git` probe; the allowed set is bwrap/claude/git/sh). Limit: comm sampling cannot distinguish the CLI's own `sh`/`git` from a tool shell, so the stream validator (no `tool_use` other than `StructuredOutput`) is the primary control and process sampling is defence in depth.
- **Transient canary failures do not latch (ruling 9 refinement).** The gate latches only on `sandbox`, `cli_version`, `auth` or schema failures (or a gate exception). A canary that ends in CLI `exit` or `timeout` raises `GateUnavailable`: no latch, parsing is skipped for that run (`gate_unavailable`, run `done`), `verify` reports `errors: ["gate_unavailable"]`.
- **Gate evidence is per parser key, the latch is global.** Evidence is stored as `gate-<hash>.json` (hash over argv template, sandbox flag and config dir), so `verify` never overwrites the worker's or the operator's evidence; the gate key hashes the contents of the login directory's files up to 1 MiB (`size:mtime_ns` above that), excluding the top-level `.credentials.json`, plus the argv sha256, the sandbox flag and the config dir. This bullet supersedes ruling 9's "config dir mtime" and `gate.json` wording. `parser-disabled.json` stays one global latch. Running the unsandboxed parser needs `STATEMENT_PARSER_ALLOW_UNSANDBOXED=true`.
- **Verify ordering.** `verify` parses (or loads the sha256 + parser-version cache) first with no database connection, then opens one short `REPEATABLE READ READ ONLY` transaction for matching, one savepoint per statement. Report counters: `lines` excludes subtotals; `Malformed` and `ExtractTimeout` count as errors, not `too_large`. The folder filter of `export-masked` is a prefix match. Raw (encrypted) PDFs are retained under `verify_dir/pdf-cache` and `state_dir/inbox` (0700); purge instructions are in `deploy/statements/README.md`.
- **Tests.** `tests/worker/__init__.py` is deliberately absent: `pythonpath = .` makes `worker/` importable, and an `__init__.py` there would shadow the package.

### R1c implementation notes (2026-10-12, PR "R1c")

The action engine, owner actions, agent proposals, policy engine (shipped off), statement confirm, manual statements and the matching-rule fixes were built under the following rulings, recorded from the implementation plan (rev 9, after the Multica reviews AGENT-101 to AGENT-104). Numbers are the plan's; a ruling later narrowed by another is given in its final wording only. No Alembic revision: every table and column exists since R1a, the new settings are JSON keys in `reconciliation_settings.data`, and `settlement_service.refund` gained a keyword `source` (default `"manual"`, unchanged for every existing caller).

**What the 2026-10-10 verify run found (counts only).** 510 statement PDFs were parsed and matched read-only: 34 % of lines matched; 147 bank `payment` lines had no gate and could never be claimed; 0 % of the lines whose ledger side is a scheduled instance (將來 and other recurring transfers) matched, because instances were never standalone; and the Type3-font statements (渣打, some 富邦, 聯邦, 國泰 card) had no text layer. Rulings 1 to 4 and 17 answer the first three; the fourth is deferred (below).

**Matching rule fixes (1–4, 17).**
1. **Bank gates.** A bank statement prints a card auto-pay or a loan repayment as `payment` and a debit-card spend as `purchase`. Final gates (ruling 17 narrowed ruling 1): `BANK_GATES["payment"] = {settlement_out, transfer_out}` (never a plain `expense`) and `BANK_GATES["purchase"] = {expense}`; a `payment` line plus an unrelated same-amount `expense` stays `line_unmatched`. The representation rule stays `payment` for `payment` lines and `exact` for `purchase`.
2. **Recurring instances are standalone.** `matching.InstanceRef` gains `definition_kind` (`recurring`|`installment`); `_standalone` rejects only installment-definition instances. §6.2's "not listed in any `posted_entry_ids`" is narrowed to installment instances: a recurring transfer or expense posted by the scheduler is an ordinary entry for matching.
3. **Loan installment groups.** A bank `payment` or `withdrawal` line may claim a complete `installment` group (every top-level member unclaimed, on a participating account and in the statement currency, all carrying an instance of the same definition) when `Σ member.flow == line.flow`: kind and rule `installment_group`, scored with `_score`. Member kinds are not gate-checked (`payable` + `interest`). Card statements never use it; partial, mixed-definition and non-summing groups are never admissible.
4. **Sibling accounts (綜合月結單; owner choice C → R1c).** The admin setting `account_siblings: {"<account id>": [account ids]}` (same currency, not archived, distinct, not the key). `reconciliation_service` adds `context.sibling_candidates` (at most 5 `{entry_id, account_id, flow, posted_date}`: unclaimed, top-level, ungrouped, equal absolute flow, within `exact_window_days`) to `line_unmatched` cases of statements whose account has siblings. `match` accepts such an entry only with `allow_sibling=true` (never in a proposal); coverage snapshots keep the entry's own `account_id`; siblings are never in the automatic population.

**Action engine (6–7, 18, 24–26, 31, 36).**
6. **Action rows are inserted first** (status `applied`) inside the apply transaction, so the partial unique index `ux_reconciliation_action_effect` refuses a duplicate effect (422 `duplicate_effect`) before any ledger write and the row id exists for the `app.reconciliation_action_id` GUC. A failure rolls the row back with everything else: no `failed` row is written in R1c (the enum value stays unused); a policy candidate that fails is rolled back and audited `policy_skipped {code}`. `uq_reconciliation_action_idempotency` is unconditional, so a key is never reused: a revert bumps `case.version` and a later re-apply computes a new key. Both idempotency lookups (before prepare, and under the lock) match any status: `applied` replays (200), `reverted` is 409 `action_reverted`, other 409 `action_failed`. The key is `sha256("{case_id}|{case_version}|{action}|{canonical params JSON}")`.
7. **Effect slots** (`effect_slot`): see 31 for `match`, `unmatch`, `dismiss`, `defer_next_period`; `create_entry`/`create_refund`/`create_system_entry` → `create`; `attach_fee` → `fee`; `adjust_amount` → `amount`; `move_account` → `move`; `split_entry` → `split`; `balance_adjustment_asof` → `balance`; `link_installment_plan` → `plan`; `revert` → `r<reverted action id>`. Entry-keyed cases (no `event_id`) rely on the idempotency key only (NULLs are distinct in the index).
18. **Creation-family exclusion.** Under the statement lock the engine refuses any creation action when an `applied` action with slot `create` exists for the same `event_id`, whichever action it was (422 `duplicate_effect`).
24. **Idempotency is re-checked under the statement lock**, so a concurrent identical request replays instead of hitting `case_closed`.
25. **Revert bookkeeping and FX pairs.** `after["coverage_ids"]` and `touched_entry_ids` are recorded for every action including coverage-only ones; revert re-reads the status under the lock and ends with `assert_conserved`; `adjust_amount` on an entry with `original_currency` against a line without a foreign amount is 422 `fx_pair_required`.
26. **The writer barrier of `balance_adjustment_asof` is transaction-scoped** (`coverage_service.take_barrier_xact`: `SET LOCAL lock_timeout = '5s'` + `pg_advisory_xact_lock` in a savepoint; 409 `sweep_barrier_busy` on timeout), released by the router's commit or any rollback on the same backend: no `finally`, no pooled-connection leak, no writer window between return and commit.
31. **Effect slots for non-ledger actions are per case version.** `match`, `unmatch`, `dismiss` and `defer_next_period` use the ruling 36 slot; ledger-effect actions use their fixed slot. A reopened case (new version) may be matched again; the key still replays within a version. Coverage `match_kind` by actor: owner → `manual`, policy-applied agent proposal → `agent`, policy's own creations → `auto` (superseded by R1d item 1: every policy apply writes `agent`); ruling 16's preservation covers `manual` and `agent`.
36. **Coverage-only effect slots are `c<case.id>v<version>`** (Multica AGENT-107): the partial unique index keys `(event_id, action, effect_slot)`, not the case, and `_write_cases` replaces a swept-open case with a new case at version 1 on the same event, so a bare `v<version>` refused the owner's match on the replacement as `duplicate_effect`. The engine refuses a slot longer than `effect_slot`'s 16 characters (a programming error). Reverts are also refused (422 `not_revertable`, `later action <id>`) while any later applied non-revert action exists on the same case, so a row-less `defer_next_period` or `dismiss` cannot be reverted over a later resolution of its case.

Also taken in the engine: the lock order is the shared import key → `policy_budget` row (policy only) → statements ascending (both for `move_account`), each swept → the case → schedule definitions/instances → entry groups ascending → entries in one ordered select; the schedule, group and entry locks are `NOWAIT` (a ledger delete holds the entry and waits on the coverage/case rows the action already holds through `ON DELETE SET NULL`), `LockNotAvailable` → 409 `action_busy` (`schedule_locks.lock_definition`/`lock_instance` gained a `nowait` keyword, defaults unchanged). Snapshot conflict (C6): `prepare` captures the expected snapshot set without locks and the engine compares it with the `before` re-read under the locks (409 `snapshot_conflict`). A reconcile run inside an action never waits at the writer barrier (`barrier_wait=False`).

**Actions (8–9, 12–14, 19–20, 32–34; 15–16).**
8. **Historical statements:** `match`, `unmatch` and their reverts only (they are coverage); every other action is 422 `historical_statement`. Cases do not exist on historical statements, so R1c exposes actions through cases only and historical statements stay read-only (see "Deferred").
9. **`create_refund` source:** `settlement_service.refund` gained `source: str = "manual"`; the action passes `"statement"`; the refund rules stay the settlement service's.
12. **`move_account` target statement:** the target account's statement whose `[period_start, period_end]` contains the entry's `posted_date` (same currency), if any; both statements are locked ascending and both are re-reconciled with `locked=True` in the apply transaction. A target account that is part of the case statement's population, and entries with `group_id`, `parent_entry_id`, `transfer_group_id`, children or a schedule instance, are 422 `not_movable`.
13. **The case DTO is the full row** (`statement_id`, `revision_id`, `resolved_by`, `resolved_action_id`, `resolved_at`, `deferred_to_period_end`, `deferred_to_statement_id`, `note`, `pending_proposals`) and `actions_allowed` is computed by the registry from the case kind, status and context; R1b's `CaseOut` field names are kept.
14. **Reverts.** Reverting a `match`/`unmatch` needs the rows unchanged versus `after` and the entry still unclaimed/claimed as expected; reverting a creation deletes through `delete_entries_cascade` only when the created rows equal `after`; reverting `split_entry` restores the anchor exactly and deletes the other members only when every member and child equals `after`; reverting `link_installment_plan` deletes the map row and re-reconciles; a revert of a revert is 422 `not_revertable`; `balance_adjustment_asof` revert deletes the adjustment when unchanged.
15. **C4 through the writer barrier, not a generation** (replaces the R1a `balance_generation` derivation, ruling 5). `balance_adjustment_asof` takes the account row `FOR UPDATE` and then the exclusive writer barrier (ruling 26) before reading the balance: every in-flight ledger writer holds the shared barrier until its commit, so once the exclusive lock is held the READ COMMITTED balance is complete and no writer can commit until the action commits. It is 422 `dirty_disabled` while `dirty_enabled` is false (the triggers would not take the barrier). The C4 "retry ≤ 3" clause is dropped.
16. **Manual coverage survives reconcile.** `reconcile` treats lines with active `manual` or `agent` coverage as already claimed (excluded from the matcher input, their rows out of the candidate population, never released by `_write_coverage`); only the sweep (a dirty edit on a covered row) and lineage release them. Sibling-account rows therefore stay claimed.
19. **`split_entry` is reachable and exactly invertible.** Allowed on `amount_delta` and on `line_unmatched` whose `candidates`/`context` name the entry. Preflight refusals (422 `not_splittable`): children, a reward-rule link, `original_currency`, settlements or refunds, a group, a parent, a transfer group, a schedule instance, a non-editable kind or a protected entry. The engine consults `Effect.resolves_case`: split resolves the case only when a member's amount equals the line and the claim is written; otherwise the case stays open with `context.split_group_id`.
20. **`attach_fee` is bundled-only.** Allowed on `amount_delta` with `context.fee_matches is True` and `params.entry_id == context.entry_id`; the line must be a debit and `residual = line.flow − entry.flow` negative (422 `fee_sign` before any write); the child is written through `write_children` with `fee = abs(residual)` (stored negative); `0 < fee ≤ 0.05 × |principal|` and exact conservation (C8).
32. **`adjust_amount` records the printed-pair rate with `fx_source="manual"`:** `fx_source` has no `statement` value and R1c adds no migration; the pair itself is authoritative.
33. **`balance_adjustment_asof` takes the account row `FOR UPDATE` first, then the exclusive transaction-scoped barrier.** An in-flight insert on the account holds `FOR KEY SHARE` on the account row and takes the shared barrier in its AFTER trigger, so barrier-first would deadlock against every plain insert; the remaining multi-account cycle (transfer legs) is resolved by the deadlock detector aborting one side.
34. **`statement_conflict` cases resolve only through `resolve_conflict`** (`dismiss` is not offered for that kind). `keep=new` refuses a revision whose guardrails failed (409 `conflict_guardrail_failed`, R1a erratum); on either outcome every other open `statement_conflict` case of an older revision is superseded (audit `conflict_superseded`) and, for `keep=current`, those revisions are rejected too, so `conflict_open` and the open conflict cases never diverge.
23. **Revision conflicts are resolved by an action.** `resolve_conflict` `{keep: current|new}`: `new` runs `statement_revision_service.promote_revision` (the "becomes current" branch of `submit_revision` extracted; persisted rows only, ruling 28), `current` rejects the revision and keeps the statement `reconciled`; either resolves the case. Not revertable.

**Proposals (21, 27).**
21. **Proposal mutations are serialized.** `create_proposal`, `apply_proposal` and `reject_proposal` lock the statement `FOR UPDATE` then the case `FOR UPDATE` (the engine's order) and re-validate status and version after the locks. Supersession on read is written and committed by the list/detail/apply routes before any conflict can be raised. Id scoping inspects every id-typed param by type (`entry_id`, `original_entry_id`, `group_id`, `line_id`, `definition_id`, `account_id`) against the case's candidates, context, line and entry (422 `id_out_of_scope`); `category_id` and `project_id` are free choices checked by the action; `allow_sibling` is refused (422 `sibling_not_proposable`).
27. **Prepare never commits the request session**: FX quotes run on a separate `SessionLocal()`; the engine re-locks and re-validates the proposal row after the statement lock (409 `proposal_not_pending`, `proposal_superseded`, `proposal_mismatch`).

**Policy (10, 22).**
10. **Policy month** = the calendar month of the application day (`date.today()` under the `today` fixture), not the statement period; one `policy_budget` row per `(month, currency)`, inserted `ON CONFLICT DO NOTHING` then locked `FOR UPDATE` before the statement lock.
22. **Policy re-checks under the lock.** `engine.apply_action` accepts a `precheck` run after the statement lock and the case checks; policy passes a closure that re-validates the enabled flags, statement exclusions, the case still open and of the expected kind, the per-statement caps counted from applied `actor='policy'` rows under the lock and, for an agent `match`, the single-admissible validator (409 `not_single_admissible`); the budget row is locked before the statement lock but incremented only after the precheck passes. Agent-accepted `match` is capped by `policy.actions.match.max_amount` (new key, default `"0"` = never). The policy ships off: `enabled=false` and every per-action flag false; `accept_agent_proposals=false` and, even when true, only `match` on `ambiguous` with one admissible representation. `run_policy` commits per candidate (the one documented exception to "services never commit") and is only called by routers after the matching transaction committed; `run_policy_safe` never fails the caller.

**Confirm and deferrals (11, 28–30; 23 and 34 above for conflict resolution).**
11. **Confirm and deferrals.** Confirm first resolves this statement's incoming deferral links (earlier statements' `deferred_next_period` cases pointing here): a deferred entry claimed here → the earlier case stays resolved and gets `context.resolved_in_statement_id`; still unclaimed → the earlier case reopens (`open`, `version + 1`, explanation cleared, `context.reopened_by_confirm_of=<sid>`), the earlier statement's counts are recomputed, and this confirmation proceeds. Confirm discovers every earlier statement id before taking any statement lock, locks all ascending (sweeping each), then re-validates the link set (409 `confirm_retry`).
28. **`promote_revision` activates persisted rows only**; `_write_lines_and_lineage` is split into insert and activate.
29. **Incoming deferrals are a read-model signal, not a flag.** `needs_recheck` keeps its R1b meaning only (matching must run again: set by the sweep's population changes and by `unmatch`; discharged solely by a completed `reconcile`, which clears it as its last step). `_recount` is counts-only; the engine and confirm use it. A deferral link to an already `reconciled` target sets nothing; the read model exposes `incoming_deferrals_pending` on `StatementOut`, and confirm processes those links (ruling 11) before its checks; incoming deferrals are never a refusal reason, a dirty `needs_recheck` still refuses. Linking writers serialize with confirm through the target's statement row lock (`_link_earlier_deferrals` under the target's lock; `fill_deferral_links` locks each target `FOR UPDATE`, one target per savepoint, and re-reads it before linking; `_write_deferrals` never fills `deferred_to_statement_id`).
30. **Promotion updates existing lineage rows** rather than inserting duplicates.

**Derived generation (5, 15, 33).** Ruling 5 retires R1a's derived `balance_generation` for good: the writer barrier of rulings 15, 26 and 33 replaces it, and the account-row-then-barrier order is the only one that does not deadlock plain inserts.

### R1d design (2026-10-12, PR "R1d" — policy-readiness fixes)

Scope: the "Deferred from R1c" items that must land before `settings.reconciliation.policy.enabled` is ever turned on, plus the three concurrency/consistency items found by the R1c final review. No migration, no new setting, no env change; the feature flag and the policy stay off. Out of R1d, still deferred: budget refund on revert (the monthly total is a ceiling on spend), separate FX fee lines and credit residuals, `move_account` typed exceptions, the historical-statement line route (R3 asks), card-identity ambiguity hints, OCR.

1. **Policy coverage survives a reconcile (R1c final review I2).** Every claim written by an action whose actor is `policy` gets `match_kind='agent'`: ruling 31 kept `agent` for proposal applies only and used `auto` for the policy's own `create_system_entry` / `attach_fee` claims, which the next reconcile then released and rewrote as fresh `auto` rows (`_write_coverage` keeps an `auto` row only when it equals the matcher's own representation), so the action's stored `coverage_ids` were gone and its revert refused. `OWNED_KINDS = ("manual", "agent")` therefore keeps the policy's claims across reconciles exactly like the owner's, the stored ids stay valid, and the revert path is unchanged: a dirty edit of the booked rows still releases the claim through the sweep and the revert is then refused on the snapshot (`snapshot_conflict`) or the released coverage (`not_revertable`), which is right. `match_kind='agent'` reads as "automation's decision, kept until the owner reverts it" (the policy is the agent's non-interactive half). Acceptance: policy apply → owner reconcile → claim ids and kind unchanged → revert succeeds and the line is unclaimed again; the same for a policy `attach_fee`; owner apply → reconcile → revert unchanged.

2. **`supersede_stale` takes statements, then cases, then proposals (R1c final review M6; AGENT-109 Must 1).** The helper first selects the statements of the cases that have a pending proposal at an older `case_version` and locks them ascending, then those cases ascending, then updates their proposals, audits and reopens idle cases — `FOR UPDATE SKIP LOCKED` on both the statements and the cases when called without `case_id` (the list routes and the apply-refusal path: a row some other transaction holds is left to that transaction's own path or the next call) and `FOR UPDATE` when scoped to one case (confirm, which already holds the statement; `get_case`; the policy after a rollback). The statement lock is not optional: every `reconciliation_audit` row references its statement, and the insert takes `FOR KEY SHARE` on that row, which conflicts with another transaction's `FOR UPDATE` — a helper holding only the case while an engine or `create_proposal` call holds the statement and waits for the case would deadlock on the audit flush. With the statement taken first the helper's order is a prefix of the engine's (statement → case → proposal → rows) and of `create_proposal`'s (`_lock_case_chain`), so no cycle exists. Because the global form skips held rows, `list_proposals` filters out pending proposals whose `case_version` is behind their case (they read as absent, never as `pending`); they are superseded durably by the holding transaction's own path (the engine supersedes the case's other pending proposals on apply) or by the next call (ruling 21's durable supersession is kept: the route commits what it could lock). Acceptance: a race where another transaction holds the statement but not the case — the scoped helper waits and then supersedes; the global helper returns 0 at once and the listing hides the stale proposal; a race where another transaction holds the case only — same outcomes; no deadlock in either.

3. **Reverting `link_installment_plan` releases the plan's claims everywhere (Task 5 review #2; AGENT-109 Must 3; AGENT-110 Must 1).** The revert's lock targets add (a) the plan's schedule definition **FOR UPDATE** (not the engine's usual FOR SHARE: posting an instance takes the definition FOR SHARE, so the exclusive lock freezes the plan's posted-entry set for the rest of the transaction — a posting in flight makes the revert 409 `action_busy`, NOWAIT as every row lock after the case), (b) every posted entry of the definition as discovered before the locks (`NOWAIT`: a reconcile claiming one holds it first → `action_busy`), and (c) every other statement of the account holding an active installment-rule claim on one of those entries, locked ascending with the case's statement (each swept). `installment_plan_map` is per account and a template may post to several accounts, so (b) and (c) are scoped to the map's account: the entries are only those on the account's participating accounts (`coverage_service.participating_accounts`, the matcher's population for its statements) and the statements only the account's own — another account's map on the same definition keeps its claims (AGENT-111 Must); the definition lock in (a) stays per definition. Before any mutation the invert re-derives, under those locks, the posted-entry set and the other-statement set: an entry or statement that is not in the engine's lock set (an instance posted, or a claim committed, between the unlocked discovery and the locks) is 409 `action_busy` ("retry": the next attempt discovers and locks the full set — nothing is handled in place after the row locks). A claim producer on another statement always locks its candidate entries `NOWAIT` before it reads the plan map (`reconcile`), so with the definition frozen and every posted entry held, either it is `reconcile_busy`, or the revert is `action_busy`, or its claim is committed and visible to the re-derivation: an uncommitted claim can never survive the map's deletion. Then the invert deletes the map, reconciles the case's own statement in-action as today, releases the other statements' installment claims on the plan's entries (reason `plan_unmapped`) and sets their `needs_recheck=True`; the engine recounts every locked statement. No in-action reconcile of other statements (unlike `move_account`, whose single target is known) and no case written on them — this differs from the dirty sweep, which reopens or creates a `recheck` case: here the next reconcile raises the `installment_unmapped` case again. A statement that was already `reconciled` keeps that status (the dirty sweep does not change it either), its `matched_count` drops, `needs_recheck` refuses confirm (`confirm_refused`, check `needs_recheck` false) until its next reconcile, which opens the case and clears the flag. Acceptance: a plan claimed on two statements → revert → both claims released, the second statement flagged and its next reconcile opens the installment case again; the same with the second statement confirmed beforehand (status kept, confirm refused, then reopened); bounded races: the second statement's reconcile holding an uncommitted claim → the revert is `action_busy`, map intact, the retry after its commit releases the claim; the revert open → that reconcile is `reconcile_busy`, and after the commit no claim is written; an instance posted and claimed (uncommitted) after the revert's discovery → the revert is `action_busy` with nothing mutated, and the retry releases the claim; a definition posting to two cards, each linked through its own map → reverting one card's link leaves the other card's map, claims, counts and flag untouched and its link revertable.

4. **`attach_fee` residual recomputed under the lock (Task 10 #3).** `policy_service._amount_now` for `attach_fee` returns the absolute difference |entry.amount − line.flow_amount| (`_fee_now`) read under the statement lock instead of `case.context.residual` (written at reconcile time; an entry edit after that reconcile makes it stale until the next sweep). A changed residual is `candidate_changed` (skipped, audited), so the budget is charged with the fee the action will actually book.

5. **`policy_skipped` audited once per case version (Task 10 #5; AGENT-109 Must 2).** The skip audit carries `case_version`; a skip is not audited again when an audit row with the same `(case_id, case_version, code, reason)` exists. The read-version → check → insert sequence runs under the case's statement lock and then the case lock (`FOR UPDATE`, the engine's order, so the audit's `FOR KEY SHARE` on the statement is already held) in the skip's own transaction (it runs after the candidate's rollback and commits itself), so two concurrent runs serialise and the second one sees the first one's row. The run result still counts every skip.

6. **The engine requires a budget for the policy actor (Task 10 #7).** `apply_action(actor='policy', budget=None)` is 422 `budget` ("the policy must spend the policy budget"), the mirror of the existing "only the policy spends the policy budget" check (an owner apply with a budget stays 422 `actor`).

7. **Agent proposals are proposals from propose-only tokens (Task 10 #10).** `accept_agent_proposals` considers only pending `match` proposals whose `author` label is configured with the propose scope and **without** the write scope; proposals by an owner token (write scope) are the owner's own drafts and are not auto-applied. With scopes unconfigured (compatibility mode) every non-policy author counts as an agent, as today.

Review focus for the plan: item 2's statement → case → proposal order against every caller (SKIP LOCKED only in the global form; the audit FK), item 1 against ruling 16's `_write_coverage` keep-set and the existing `auto` assertions in the tests, item 3's entry locks as the serialisation with other statements' reconciles (late-discovered statements are 409, never handled after the row locks), and item 5's serialisation.

### R5 OCR design (2026-10-14, PR "R5" — statements without a usable text layer; rev 3 after AGENT-118 rounds 1–2)

**Problem.** Some issuers print statements with a Type3 glyph font that has no ToUnicode map and hundreds of inline glyph images; text extraction yields nothing (中信卡) or `(cid:NNN)` garbage (中信存款, 元大卡, 華南卡, 遠東存款). On 2026-10-14 that is 12 files; 中信卡 produces one every month. A read-only spike that day (RapidOCR in a throwaway venv as `homehub-worker`): 12/12 read at 0.91–0.96 mean confidence in 8–29 s per file, 12/12 parsed by the pinned parser with the right kind and period, 12/12 pass the server guardrails once the labeling rule of R5.5 is applied. The balance equation holding means the amounts read are right; it does not prove completeness (offsetting omissions also balance).

**Decisions.** OCR runs locally (owner, option A): page images never leave the host. Rendering and recognition run in a dedicated child process without network access, with a minimal environment and read-only binds limited to the runtime, under resource limits, with a parent-enforced deadline and bounded I/O (AGENT-118 rulings). OCR text is normalised, masked and guarded before the sandboxed parser or a verify snapshot sees it (§11 unchanged). An OCR'd statement is treated exactly like a text-layer one (owner): the guardrails are the check, no forced `parse_review`, provenance is visible on the revision. No migration.

**R5.1 Trigger (`worker/pdf.py`).** `extract` raises `NoTextLayer` when page 1's stripped text has fewer than 200 characters (as implemented: `len(text.strip())`) **or** when `(cid:` tokens are at least 10 % of its whitespace-separated tokens. The rule looks at page 1 only, like the existing one: a file whose page 1 reads but whose later pages are garbage is parsed from the text layer; its guardrails may fail (needs_review) or may pass with rows missing — the existing contract, unchanged by R5. Either way the file keeps `has_text_layer=false`.

**R5.2 OCR child (`worker/ocr_child.py`; pure text helpers in `worker/ocr_text.py`; parent `worker/ocr.py`).**
*Start.* The parent runs `python -B -m worker.ocr_child` with an explicit minimal environment (`PATH=/usr/bin:/bin`, `HOME=/tmp`, `LANG=C.UTF-8`, `PYTHONDONTWRITEBYTECODE=1`, `PYTHONPATH=/work`) — never the worker's environment, which holds the verify DB URL and other configuration — and, when `cfg.parser_sandbox` is on, under bwrap: `--unshare-all` (no `--share-net`), `--die-with-parent --new-session --cap-drop ALL`, read-only binds of `/usr`, `/lib`, `/lib64`, the interpreter's base prefix, the venv prefix (site-packages carry the models) and the `worker/` package directory at `/work/worker` (nothing else of the checkout, no `/etc`, no home, no state or config directories), `--tmpfs /tmp`, `--proc`, `--dev`, `--chdir /work`. The child is its own session; the parent kills the session group.
*Protocol.* Stdin: one JSON header line (`password`, `scale`, `max_pages`, `max_pixels`, `threads`, `rlimit_as_mb`, `rlimit_cpu_s`), then the raw PDF bytes. Stdout: exactly one JSON line; anything else (more lines, a non-object, missing or mistyped fields, a confidence outside 0..1, a page count outside 1..`max_pages`, text over the cap) is `malformed`. Stderr is discarded by the parent in production.
*Order inside the child.* At import: `RLIMIT_CORE=0` and baseline `RLIMIT_AS`/`RLIMIT_CPU` (2048 MB / 150 s). Then: read the header line (bounded, 4 KB) → apply the header's limits → readiness: import pypdfium2, numpy, rapidocr_onnxruntime; build the engine (`intra_op_num_threads = threads`, bundled PP-OCRv4 models, nothing downloaded); self-test on a 32 × 32 white image. A failure here prints `{"ok": false, "code": "unavailable"}` and exits **without reading the PDF**. Only then the PDF bytes are read: pages > `max_pages` → `too_large`; per page, `ceil(w·scale) × ceil(h·scale)` (finite, positive) > `max_pixels` (default 30 000 000) → `too_large` before any allocation; render at `scale` (3.0 = 216 dpi) to an in-memory RGB array; recognise; rebuild rows (`ocr_text.layout`, purely geometric); zero boxes on a page is allowed and counted; zero boxes in the file or mean confidence < 0.80 → `low_confidence`; a pdfium/engine exception on a page → `malformed`. Success: `{"ok": true, "pages", "empty_pages", "boxes", "mean_confidence", "text"}`. Nothing is written to disk.
*Parent bounds and outcomes.* Stdin is written from a thread; stdout is read with selectors and counted as it arrives: past 2 MB the parent kills the child and the file is `malformed`. The wall-clock deadline (`cfg.ocr_timeout_s`, default 120 s, covering load and self-test) kills the session group with SIGKILL and reaps it (bounded wait); timeout → `OCRTimeout`. Exit classification: a resource kill (SIGKILL, SIGXCPU — directly or as bwrap's 128+n) → `OCRTimeout`; a crash signal (SIGSEGV, SIGABRT, SIGBUS, SIGFPE, SIGILL) or any non-zero exit → `Malformed`; `code` `unavailable` → `OCRUnavailable`, `too_large` → `TooLarge`, `low_confidence` → `OCRLowConfidence`, `malformed`/invalid response → `Malformed`. Exceptions are built outside any active exception and carry fixed phrases: no child output, no stdin, no library text (`__cause__` and `__context__` are None). `OCRUnavailable` is cached for the rest of the current run and reset at the next run boundary (`poll` executes several runs in one process).

**R5.2a Normalisation of OCR text (`ocr_text.normalise_text`, `LAYOUT_VERSION`).** Applied per line, before masking, on the OCR branch only:
1. whitespace between two all-digit tokens (ASCII spaces, tabs, U+3000) collapses to one space, so split card and account numbers take the shape the masker's "groups of ≥ 3 digits joined by one space" rule and its date/short-reference exclusions already handle (text-layer statements arrive in that shape today);
2. identifier-scoped OCR confusables: a token of 4+ characters drawn from `0-9 O o I l |` with at least two ASCII digits maps `O/o → 0`, `I/l/| → 1` (merchant text is never rewritten);
3. a token `[A-Z][12]\d{0,8}` followed by digit tokens whose concatenation is exactly `[A-Z][12]\d{8}` is joined (a split ID, whether or not it is the configured one);
4. whitespace between CJK-only tokens is removed when the joined run is at most 4 characters (split holder names; longer merchant names keep their spacing).
Layout padding is otherwise kept for the parser. A compact date followed by an amount (`20260901 1234`) masks exactly as it does on the text-layer path today (the masker's `_digits` rule); real statements print dates with separators and amounts with thousands separators. Changing any rule bumps `LAYOUT_VERSION`, part of the parser version (R5.4).

**R5.2b Masking guard (`Masker.guard_lines`).** After `Masker.text`, a line whose whitespace-stripped form contains a **non-numeric** identity literal — the ID number, a holder name of ≥ 2 characters (compared with the name's own whitespace removed), or a password candidate of ≥ 6 characters containing a letter — is replaced by `[LINE MASKED]`. Numeric literals (birth dates, numeric passwords) are never guarded: after R5.2a they are contiguous and the masker's literal, birth and digit-run rules handle them with their date and amount exclusions, so a transaction row cannot vanish because a candidate equals a year or an amount. `Masker.mask_ocr(text, extra_literals) = guard_lines(text(normalise_text(text), extra_literals), extra_literals)`.

**R5.3 Pipeline (`worker/pipeline.py`).** On `NoTextLayer`, when `cfg.ocr_enabled`: `services.ocr.read(data, password)`. Outcomes: `OCRUnavailable` → `summary.errors` gets `ocr_unavailable` once, the file is left in its current status (`new` stays `new`, an existing `needs_review` row stays as it is) and counted `skipped`; the run finishes `done`; `run` exits 1 (degraded); `poll` carries the union of error codes of the runs it executed, so a degraded run followed by a clean one still exits 1. `OCRTimeout` / `OCRLowConfidence` → `needs_review/no_text_layer`, `has_text_layer=False`. `TooLarge` → `needs_review/too_large`. `Malformed` → `failed/parse` at the current parser version. Success → `Masker.mask_ocr`, the existing STDIN_CAP check, `update_file(status=unlocked, has_text_layer=False, text_chars, pages)`, the sandboxed parser, `submit_revision` with `parser="claude-cli+ocr"` and `raw.notes` = the parser's own notes plus one line `ocr: mean_confidence=0.93 boxes=262 empty_pages=0 scale=3.0`. With `cfg.ocr_enabled` false → `needs_review/no_text_layer` as today. A text-layer file makes zero OCR calls.

**R5.4 One bounded parser version.** `parse_schema.version(cli_version, model, ocr_fingerprint)` → `claude-cli-<cli[:12]>-<model[:24]>-<fp12>` where `fp12` = sha256 over the full CLI version, the full model id, the instruction, the JSON schema and the OCR fingerprint (`rapidocr-onnxruntime` + `pypdfium2` versions + `LAYOUT_VERSION`), first 12 hex. Maximum length 61, so no configuration can exceed the 64-character API/DB bound; truncated display parts cannot collide because the full values are hashed. One string for every file: an instruction, schema or OCR change re-queues files whose failure is `parse`/`guardrail`/`no_text_layer`/`too_large`; password, mapping, transient and sandbox keep their own rules; `parsed` files never re-parse. The operator gate keys on the parser argv/config (`Gate.key`): this release re-keys it because the instruction is in the argv; a later OCR-only bump does not.

**R5.5 Instruction rule (`parse_schema.INSTRUCTION`).** Appended sentence: "On a card statement every negative row is a credit: a payment received is payment, a cash-back or points credit is reward, and any other reversal (退款, 取消, 分期調整 / 轉分期 reversing a purchase) is refund; never label a negative card row balance_adjustment." A `refund` line matches only `refund` ledger candidates; no new kind (AGENT-118 agreed); two matching regressions pin it.

### R5 implementation notes (2026-10-14, PRs "R5a" #72, "R5b" #73, "R5c" #74)

**Child boundary (R5a, `worker/ocr_child.py`, `worker/ocr.py`, `worker/ocr_text.py`).** Thread setting found on this host: `RapidOCR(intra_op_num_threads=N, inter_op_num_threads=1)` with N = `STATEMENT_OCR_THREADS` (2). The venv's `bin/python` is a symlink through an unbound directory, so the parent execs the real interpreter with the site-packages (and platlib) on `PYTHONPATH`. Bind list used under bwrap: `/usr`, `/lib`, `/lib64`, the interpreter's base prefix, the venv's site-packages, and `worker/` at `/work/worker`, all read-only; `--unshare-all` (no network), `--die-with-parent`, `--new-session`, `--cap-drop ALL`, `--tmpfs /tmp`, `--proc`, `--dev`, `--chdir /work`. `--die-with-parent` is bound to the thread that spawned bwrap, so the `Engine` records its creating thread and `read`/`preflight` raise `OCRThreadError` from any other thread (fail closed; pipeline, verify and export call OCR on the worker's main thread only). Environment allowlist: `PATH`, `HOME=/tmp`, `LANG`, `PYTHONDONTWRITEBYTECODE`, `PYTHONNOUSERSITE`, `PYTHONPATH`, `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS`, `MALLOC_ARENA_MAX`. Child order: rlimits → fd 1 moved to `/dev/null` with the protocol line on a saved descriptor → readiness (imports, engine, detection and recognition on synthetic images) → byte-wise header → exact `pdf_len` → page and pixel bounds → one JSON line. Codes `unavailable`, `resource` (MemoryError or ENOMEM anywhere, also while reading the header or payload or writing the result), `too_large`, `malformed`, `low_confidence`. The parent runs `--selftest` once per run: a failed start or an invalid or non-ready answer latches `OCRUnavailable` until `reset()` at the next run boundary; a self-test that reports `resource` or hits the deadline does not latch (`OCRResource`, `OCRTimeout`). Exit classification as rev 3, plus `resource` → `OCRResource` (added by the R5a review). `Engine.starts` counts file reads, not self-tests.

**Masking (R5b, `Masker.mask_ocr`).** Span-only: NFKC, format characters and nonspacing marks dropped → confusables corrected inside digit-like runs that are at least 70 % digits or at least 12 characters long (a token of pipes only never joins) and in the digit part of an ID-shaped token → compact, alphanumeric and digits views mapped back to line positions, the compact and digits views dropping whitespace and group separators (dash, en/em dash, hyphen, minus sign, dot, middle dots, slash, pipe) → literal spans (ID, holder names, birth patterns, candidates ≥ 4 characters; span edges are ASCII letters and digits only, with the text path's date exclusions for numeric spans), any ID-shaped span whose letter may be a Cyrillic or Greek lookalike at that position only, any run of 12 or more digits → matched spans replaced, overlaps merged → the shared `text()` rules. `_EMAIL` is linear (possessive local part that cannot start inside a run; same matches; `Masker.text` untouched). The rev 3 `guard_lines`/`normalise_text` design was replaced by this span-aware masker during the R5b reviews (no `[LINE MASKED]`, no generic CJK joining). Known limitations are listed in the deploy README.

**Integration (R5c).** Trigger `pdf.is_font_garbage` (page 1, at least 10 % `(cid:` tokens). `parse_schema.version(cli, model, ocr_fingerprint)` = `claude-cli-` + cli[:12] + `-` + model[:24] + `-` + 12 hex of sha256 over the full values, instruction, schema and fingerprint (`VERSION_MAX` 64, actual maximum 61); `STATEMENT_PARSER_CLI_VERSION` and `STATEMENT_PARSER_MODEL` are charset-checked at load (`config.ConfigError`, message names the key only). Instruction sentence as R5.5; matching regressions pin refund ↔ refund only. Pipeline: `Services.ocr` (None when `STATEMENT_OCR=false`), `Engine.reset()` at every run boundary, `_ocr()` outcomes — `OCRUnavailable` → file untouched, `skipped`, `ocr_unavailable` once; `OCRTimeout`/`OCRResource`/`OCRLowConfidence` → `needs_review/no_text_layer`; `TooLarge` → `needs_review/too_large`; `Malformed` → `failed/parse`; every OCR outcome records `has_text_layer=false`. Pre-mask bound (new in R5c, defence in depth): OCR text over the parser's `STDIN_CAP` or any line over `OCR_LINE_MAX` (4 096) characters → `needs_review/too_large` without masking or parsing, because the child's text is untrusted and the masker's cost grows with the square of a line's length (measured 0.08 s at 4 000 characters before the R5b email fix). `revision_body(..., parser, extra_note)` → `parser="claude-cli+ocr"`, `raw.notes` = parser notes + newline + `ocr: mean_confidence=… boxes=… empty_pages=… scale=3.0`. `cli._bad`: exit 1 on `bad_runs`, `parser_disabled` or `ocr_unavailable`; `poll` returns the union of its runs' codes. `export_masked`: same branch, meta `extraction` and `ocr_fingerprint`, counters `ocr` and `ocr_unavailable`. Dependencies pinned in `requirements-worker.txt` (`rapidocr-onnxruntime==1.4.4`, `pypdfium2==5.14.0`, `onnxruntime==1.31.0`) and frozen in `requirements-worker-constraints-aarch64-py313.txt`. The real-engine evidence line (`RUN_OCR_MODEL_TESTS=1`, SHA, platform, Python, fingerprint) is kept in each PR's record and in the release record, not here.

**Deviations from rev 3.** `OCRResource` as a distinct retry-later outcome; the pre-mask text bound; `has_text_layer=false` on an OCR `failed/parse`; `STATEMENT_OCR_CHILD` is a string of shell words rather than a path; the self-test preflight per run; the fail-closed thread guard.
