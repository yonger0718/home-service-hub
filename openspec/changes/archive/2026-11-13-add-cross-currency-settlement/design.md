## Context

`settlement_service.settle` refuses an account whose currency differs from the target's (`_same_currency_account`). Every place that sums a debt's settlements only adds settlements in the debt's own currency: `settlement_service.open_amount`, `ledger_service._settled_sum` (open-debt filter, list and detail `open_amount`, `is_settled`) and `settings_service._open_amounts` (counterparty totals, which leave cross-currency links out). `schedule_read.loan_summary` adds `abs(amount)` of every settlement whatever its currency. The SPA settle panel lists only accounts in the entry's currency, and its 已收 / 已還 figure adds `amount` across the settled-by rows.

Production data (counts only, 2026-11-13): 11 settlements are linked to a debt in another currency, all from the MOZE backup import, none with `original_amount`, all on closed (`is_closed`) debts. No refund is linked across currencies. 5 settlements carry `original_amount`, none of them across currencies.

## Goals / Non-Goals

**Goals:** settle a receivable or payable from an account in any currency with the owner's two amounts; every open-amount figure nets that settlement in the debt's currency; existing data reads the same.

**Non-goals:** cross-currency refunds (no case yet; refunds stay same-currency); a manual 結清 / write-off; FX rates fetched for settlements (the owner types both amounts); schedule-posted repayments in another currency (schedule lines keep `currency = account currency`); a foreign-transaction fee proposal on settlements.

## Decisions

**D1 — Request shape.** `SettleIn` gains `original_amount` (unsigned `Money`, optional; JSON `null` = absent). Same currency: it must be absent, else 422 on `original_amount` (no silent ignore: a client sending it expects a conversion). Other currency: it is required, else 422 on `original_amount`. The old 422 on `currency` goes away. `amount` stays the amount that moved in the chosen account. Known clients: the SPA and schedule posting never send the field; the Hermes `homehub-api` skill does not document it today (its text is updated at rollout). `SettleIn` ignores unknown keys today, so a client that already sent a stray `original_amount` on a same-currency settle would now get 422 — none is known.

**D2 — Stored row.** The settlement keeps `currency = account.currency`, `amount = sign × amount`. Across currencies it also stores `original_amount = sign × original_amount`, `original_currency = target.currency`, `fx_rate = |amount| / |original_amount|` quantized to 10 decimals half-up, `fx_source = 'manual'`. `fx_rate` is NUMERIC(20,10): the ratio is computed and quantized under a local `Decimal` context with enough precision (`prec = 60`; two `Money` values can give a ratio near `10^20`, which the default 28-digit context cannot quantize to 10 decimals), and a pair whose quantized rate is `0` or `≥ 10^10` is refused with 422 on `original_amount` before anything is written, so neither the arithmetic nor the insert can fail with a 500. This is the transfer-leg convention (spec "Transfer endpoint"), so the existing FX line renders on the settlement's own detail with no SPA change.

**D3 — Settled value.** One rule for every reader: a settlement's settled value in its target's currency is `amount` when `currency = target.currency`; `original_amount` when `currency ≠ target.currency` and `original_currency = target.currency`; otherwise nothing. The branches are tried in that order, so a same-currency row that carries `original_amount` (the MOZE import writes FX when a record's currency differs from its account's, with `original_currency` ≠ the row's currency) still counts its `amount`. The last branch keeps the 11 imported links out of every sum, as today (their debts are closed anyway). The MOZE importer's own FIFO / overflow bookkeeping (`moze_backup_import_service`) stays same-currency and is not changed by this rule. The open amount is `|target.amount + Σ settled values|`.

**D4 — Over-settlement.** The cap compares the request's settled value (`original_amount` across currencies) with the open amount, inside the existing `FOR UPDATE` lock.

**D5 — Counterparty open amounts.** A settlement linked across currencies with a settled value is summed into the bucket of its target's currency with that value; without one it stays out. Closed debts and their settlements stay out as today. Unlinked rows (debt originals, settlements without `settles_entry_id`) keep their own currency and amount: the target is joined with a LEFT OUTER JOIN, and only the linked cross-currency branch changes bucket and value.

**D6 — Loan repaid.** `repaid` sums the absolute settled values. For a same-currency loan this equals today's figure; production has 3 loan lines and no cross-currency link on any of them (2026-11-13). `remaining` stays the positive magnitude the code and `test_schedule_read.py` already return (`loan_open_amount`, "spec §4.1b"); the main spec's "signed like the loan" wording and its `-275001` scenario were stale, and this change's delta corrects the text to match the code — the API does not change.

**D7 — SPA panel.** The 帳戶 select lists every non-archived account: the entry's currency first (current order), then the others with the currency code after the name. Choosing an account in another currency shows two amount fields: the amount in the account's currency (empty by default) and 抵銷 in the entry's currency (default the open amount, capped by it), plus a read-only conversion line in the entry detail's FX format (`fxConversionLine`: `US$20 × 32 = $640`, shown once both amounts are positive). Same-currency stays one field, unchanged. The request sends `original_amount` only across currencies. Switching to a foreign account clears the first amount (its old value was in another currency); switching back restores the same-currency default (the open amount). The first amount is parsed and serialized in the account's currency. The 抵銷 field works at the ledger's four decimals, not the currency's display decimals (the SPA's display parsing rounds USD to 2 and TWD/JPY to 0, and turns a remainder below one display unit into nothing): it is prefilled with the open amount written out to four decimals without trailing zeros (`20.0001`, `0.0001`), parsed at four decimals with exact decimal arithmetic (scaled integers, never floats, so `100000000000.0001` survives), refused above the open amount, and sent as typed at four decimals — so leaving the default always settles to exactly 0. Empty or invalid input is refused (`請輸入金額`), never treated as the full amount. The server cap stays exact.

**D8 — 已收 / 已還.** The breakdown sums the settled values of `settled_by` with D3's rule, in the entry's currency. Related lines keep each settlement's own amount and currency.

## Risks / Trade-offs

- The owner types both amounts, so a typo in either books a wrong rate. The rate line in the panel makes it visible before saving; the settlement is deleted and re-settled to fix it, like today.
- `original_amount` is also used by the entry form's FX path (`resolve_fx`) for ordinary entries. Settlements never go through it (`_assert_form_kind` refuses them), so the two meanings do not meet.
