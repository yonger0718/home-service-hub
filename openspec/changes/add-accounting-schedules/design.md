## Goals / Non-Goals

**Goals**
- Every imported loan, installment and recurring stream keeps posting after cutover, with each repayment lowering the loan's 剩餘 and booking its 利息.
- The owner can create 週期 and 分期 in the entry form, choose 自動入帳 or 提醒入帳, and manage them (pause, resume, change mode, end, edit) from 提醒中心.
- Items that need a tap wait in 待完成交易; failures are visible and retryable; nothing posts twice; no period dated before a definition existed in HomeHub posts without the owner's tap.
- Re-importing the backup during the mirror period never duplicates what HomeHub already posted and never touches local definitions.

**Non-Goals (Phase B, AGENT-57)**
- Holiday shifting (`dayAdjustmentPolicy`), interest-rate maths (本息均攤 / 本金均攤, rate changes, 寬限期, 提前償還本金, 提前繳清分期), 既有欠款分期 and 起始期數 in the form, 修改連同未來 of a period's date or rule from a single instance (amounts are in scope: D35, proposal decision 24), reward lines from schedules, push notifications, low-balance warnings on 待完成交易 (MOZE's ⚠ when an item would overdraw the account), future instances on the calendar or timeline, schedules in the CSV importer.


## Decisions

### D28. Two tables: definition (the rule) and instance (one period)
`schedule_definition` holds the rule and the payload; `schedule_instance` holds one row per period with its own state, so a posted, skipped or overridden period never depends on re-evaluating the rule. Columns (design doc §3, with the refinements marked ★):

`schedule_definition`: `id`; `moze_id` (VARCHAR(64), UNIQUE, NULL for local; the `AHPeriod` / `AHInstallment` identifier, or ★`record:<AHRecord identifier>` for a single future record without `eventID`, so the two id spaces never collide); `kind` (enum `schedule_kind`: `recurring | installment`); `name` (VARCHAR(128)); `template` (JSONB, D29); `interval_unit` (enum `schedule_interval`: `day | week | month | year`); `interval_n` (SMALLINT ≥ 1); `anchor_date` (DATE, occurrence 0 of the rule); `day_of_month` (SMALLINT 1–31, NULL = the anchor's day; monthly and yearly only); ★`first_seq` (INTEGER ≥ 1, default 1: the seq of the anchor occurrence; rebased by `PUT`, D35); `times` (INTEGER, NULL = until stopped; the total N, seqs never exceed it); `end_date` (DATE, NULL); ★`total_amount` (NUMERIC(20,4), NULL; the installment total — for a loan, the loan amount); `posting_mode` (enum `schedule_posting_mode`: `auto | confirm`, default `auto`); `status` (enum `schedule_status`: `active | paused | ended`, default `active`); ★`auto_post_from` (DATE, NOT NULL: the Taipei date the definition was created locally or first imported; the job never posts an instance due earlier, D34); `generated_until` (DATE, NULL until first generation); `created_locally` (BOOLEAN, default true; false for imported); ★`template_owner_edited` (BOOLEAN, default false; set by a period amount edit with scope `following` / `all`, D35; the importer then keeps the template amounts, D37); ★`moze_payload` (JSONB, NULL; the raw `AHPeriod` / `AHInstallment` row, kept so Phase B's rate maths need no backup); ★`review_reason` (VARCHAR(64), NULL; why an imported definition was imported paused); `created_at`, `updated_at`.

`schedule_instance`: `id`; `definition_id` (FK, ON DELETE CASCADE); `seq` (INTEGER); ★`rule_date` (DATE; the rule's occurrence date, set at generation or import, never changed by an instance edit); `due_date` (DATE, Taipei; = `rule_date` unless the owner moved the period; no holiday policy); `status` (enum `schedule_instance_status`: `pending | posted | skipped`); `posted_entry_ids` (JSONB array of `ledger_entry.id`, default `[]`); `acted_at` (TIMESTAMPTZ); `acted_by` (enum `schedule_actor`: `auto | owner | import` — ★`import` marks periods MOZE booked or disabled, D37; for those `acted_at` is the import's start time); `amount_override` (JSONB, NULL — ★a list of unsigned decimal strings aligned with the template's lines, because a MOZE period carries two varying amounts, repayment and interest; `"0"` means "this line is not written this period"); ★`edited_by_owner` (BOOLEAN, default false; set by `PUT …/instances/{id}`); ★`is_partial` (BOOLEAN, default false; D33); `last_error` (TEXT, NULL) and ★`last_error_at`; ★`reopened_at` (TIMESTAMPTZ, NULL; D33); ★`note` (VARCHAR(128), NULL); `moze_id` (VARCHAR(64), UNIQUE, NULL; the primary MOZE record) and ★`moze_record_ids` (JSONB array; every MOZE record merged into this period: repayment + interest, out-leg + in-leg); ★`moze_payload` (JSONB, NULL; those raw records); `created_at`, `updated_at`.

Constraints and indexes: `UNIQUE (definition_id, seq)`; partial unique `ux_schedule_instance_posted_day ON (definition_id, due_date) WHERE status = 'posted'` (a period date is posted at most once); `CHECK ((status = 'posted') = (jsonb_array_length(posted_entry_ids) > 0))`; `CHECK ((status = 'pending') = (acted_at IS NULL))`; `CHECK (is_partial = false OR status = 'posted')`; index `(status, due_date)`; GIN `ix_schedule_instance_posted_entries ON posted_entry_ids jsonb_path_ops` for the reverse lookup `posted_entry_ids @> '[<id>]'` (D33, D40). The alignment of `amount_override` with the template's lines spans two tables, so the schedule service enforces it on every write (422 naming `amounts`), and `PUT` on the definition realigns the overrides of its remaining pending instances (D35).

### D29. Template line shape
`template = {"lines": [Line, …], "description": str | null, "tags": [str]}`, 1–10 lines. `Line` has exactly these keys (absent optional keys are stored as `null`):

| key | type | used by |
|---|---|---|
| `kind` | `expense` \| `income` \| `receivable` \| `payable` \| `transfer` \| `repayment` \| `collection` \| `interest` | all |
| `account_id` | int | all (transfer: the from-account; repayment / interest: the paying account) |
| `to_account_id` | int \| null | `transfer` only, required |
| `to_amount` | decimal string \| null | `transfer` only; required when the two accounts' currencies differ, else defaults to `amount` |
| `counterparty_id` | int \| null | required for `receivable` / `payable`; ignored for `repayment` / `collection` / `interest` (the loan's is used) |
| `category_id` | int \| null | must match the line's ledger kind; `interest` defaults to the system 利息 category |
| `project_id` | int \| null | all |
| `amount` | decimal string, unsigned, > 0, ≤ 4 dp | all; in the account's currency; the server applies the sign |
| `currency` | string | must equal the account currency (no FX in schedules; cross-currency only via `transfer` + `to_amount`) |
| `loan_entry_id` | int \| null | `repayment` (a `payable` original) / `collection` (a `receivable` original), required |
| `name` | string \| null | entry name; NULL → the definition's `name` |
| `merchant` | string \| null | entry merchant |

Lines carry no FX, fee / discount children, split members, reward rules, photo or invoice fields; those are Phase B, and the form hides them on the 週期 / 分期 tabs (D43). Line kind → ledger write (D31): `expense` / `income` / `receivable` / `payable` → one entry of that kind; `transfer` → a transfer pair; `repayment` → a settlement (`payable`, `−amount`, `is_settlement`, `settles_entry_id = loan_entry_id`); `collection` → a settlement of a receivable (`+amount`); `interest` → an `interest` entry of `−amount` carrying the loan's counterparty (the ledger delta allows `counterparty_id` on `interest`). MOZE record types map to line kinds 0 → `expense`, 1 → `income`, 2 → `transfer`, 3 → `receivable`, 4 → `payable`, 5 → `collection`, 6 → `repayment`, 15 → `interest`; 14 (reward) is ignored (design doc §6); 7, 12, 13, 16 are not expected as future records and are reported as unsupported.

**References.** While a definition that is not `ended` references an account, category, counterparty, project or loan entry in its template, archiving or deleting that row is refused with 409 naming the definition (deleting a referenced loan entry included), and the backup importer counts template references as usage (never deleting or archiving them as unused). A split `PUT` on a group whose members a posted instance lists is refused with 409 naming the instance (the owner uses 編輯這一筆, D35).

**Amount precedence** for a line in a period: the owner's instance edit (`edited_by_owner`) over the imported `amount_override` over the template's `amount`; a re-import never overwrites an owner edit (D37). Status precedence: an `auto` or `owner` action is never overwritten by an import.

### D30. Instance generation: next occurrence after the latest instance, 13-month horizon, monthly clamping
Occurrence k (k = 0, 1, …) of the rule has date:
- `day`: `anchor_date + k·n` days; `week`: `anchor_date + 7·k·n` days;
- `month`: year/month = anchor's month + k·n, day = `min(day_of_month ?? anchor day, days in that month)` — always computed from the anchor, never from the previous occurrence, so a 31st clamps to 2026-02-28 and returns to 2026-03-31;
- `year`: anchor year + k·n, same month, day clamped the same way (02-29 → 02-28 in common years).

Generation finds the latest existing instance of the definition (any status) by `rule_date` and inserts, one by one, the rule's next occurrence strictly after that `rule_date` (so moving a period earlier or later never repeats or shifts the series) (occurrence 0 when the definition has none), with `seq` = the previous maximum `seq` + 1 (`first_seq` for the first), while `seq ≤ times` (when set), `date ≤ end_date` (when set) and `date ≤ horizon`, where `horizon = today + 13 months` (same day-of-month, clamped). An occurrence whose date equals a posted instance's `due_date` is not generated (no seq consumed). It then sets `generated_until = horizon`. It never deletes, moves or re-dates an existing instance, so an owner's date edit on one period cannot shift later ones. Definitions `active` and `paused` are generated (a paused row still shows its next date); `ended` ones are not. A definition becomes `ended` automatically when its last seq (`times`) or the last occurrence ≤ `end_date` exists and no instance is `pending`. Imported installments already hold every period MOZE generated (to 2036-08); generation adds nothing for them.

### D31. Posting: one transaction per instance, existing services, `source = 'schedule'`
`post_instance(instance_id, actor)` runs in one transaction:
0. Take `pg_try_advisory_xact_lock_shared(IMPORT_LOCK_KEY)`; when an import holds the key, refuse with 409 `import_running` (D32).
1. `SELECT … FOR SHARE` the definition (`FOR UPDATE` when the template has a loan line, because step 4 may end the definition; see D32), then `SELECT … FOR UPDATE` the instance (the job adds `SKIP LOCKED`, D34). If the instance is not `pending` → 409 `already_posted` / `skipped` (idempotency: a second caller waits on the row lock and then sees `posted`).
2. Resolve each line's amount by the precedence of D29; a line whose amount is `"0"` is not written.
3. Re-validate every line as at save time (the account, category, counterparty, project and loan entry exist; the account is not archived; currency matches). A failure names the line (`lines[1].account_id`).
4. Loan lines: when the loan entry `is_closed` or its open amount is 0, the instance and every later pending instance of the definition are `skipped` with `acted_by = auto` / `owner` and `note = 貸款已結清`, the definition becomes `ended`, and nothing is written; when the open amount is below the repayment amount, the repayment is clamped to the open amount (this is also how the last period of a loan absorbs rounding, D35). Interest is never clamped.
5. Write each line through the existing services with `entry_date = posted_date = due_date`, `entry_time = NULL`, `source = 'schedule'`, `remember = False` (schedules do not move a category's default account), name `line.name ?? definition.name`, the template's `description` and `tags`: `entry_write_service.insert_prepared` for entries, `transfer_service` for transfers, `settlement_service.settle` for repayment / collection, an `interest` insert with the system 利息 category and the loan's counterparty. The services gain a `source` keyword (default `'manual'`) and settle gains an internal `check_cutover_lock=False` used only here (D36).
6. With two or more non-transfer entries written, they share a new `entry_group` (`kind = installment` for an installment definition, else `split`; `name = "<definition name> #k/N"`, or `#k` when `times` is NULL), the way MOZE packages a repayment and its interest.
7. Set `status = posted`, `posted_entry_ids` = the ids of every top-level entry written (both transfer legs, settlement, interest), `acted_at = now()`, `acted_by` (`auto` from the job; `owner` from post, catch-up, resume with backlog, repost), `is_partial = false`, `last_error = NULL`, `reopened_at = NULL`.

A repayment is refused (422) when the loan entry is missing or is not a `payable` original. On any error the transaction rolls back; a second short transaction writes `last_error` (the validation message, which names a field, never an amount) and `last_error_at`, and the instance stays `pending`. Owner actions get the 422 back as well. Multi-instance operations (catch-up, resume with `backlog = post`, the job) commit any status change first and then post each instance in its own transaction, in `seq` order, stopping at the first failure.

### D32. Lock order: import advisory key → definition → instance → the ledger's order
Every schedule write path — post, catch-up, resume with backlog, repost, reopen, skip, instance `PUT`, definition `PUT` / `end` / `pause` / `DELETE`, generation, run-now, and the entry-delete path when it touches an instance — first takes `pg_try_advisory_xact_lock_shared(IMPORT_LOCK_KEY)` and answers 409 `import_running` when an import holds it. Then, in order: the `schedule_definition` row (`FOR SHARE` when posting, `FOR UPDATE` when editing, pausing, ending or deleting) → `schedule_instance` row(s) (`FOR UPDATE`, ascending id when several) → the ledger's existing order (`entry_group` rows ascending → target entries with their transfer legs in one statement → nothing else). A settlement's `locked_entry(loan)` is the "target entries" step. The entry `DELETE` path reads, without a lock, the instance whose `posted_entry_ids` contains the entry (and its definition), then takes the shared key, locks definition `FOR SHARE` and instance `FOR UPDATE`, re-checks the containment, then continues with its existing group → entries order.
Refinements found in plan review (stricter than the text above, never weaker): a path that may *write* a definition it would otherwise hold `FOR SHARE` takes `FOR UPDATE` instead, because two `FOR SHARE` holders that both upgrade deadlock — a post or repost of a template with a loan line (it may end the definition) and the entry-delete path when the definition is `ended` (it may revive it). A loan post locks the definition's later pending instances (`seq > k`, ascending id) before `locked_entry(loan)`, so the close-out never locks a schedule row while holding the loan entry. A repost locks the loan entry in the same single statement as the period's entries it deletes, and posts against that row. No path that holds an entry or group lock ever locks a schedule row. The backup importer holds the key exclusively (it retries `pg_try_advisory_lock` for up to 30 s while shared holders finish) and, inside its ledger transaction and **before** deleting any entry, locks every schedule row it will touch — definitions by ascending id, then instances by ascending id — so the `settles_entry_id` and `loan_entry_id` re-pointing (D37) happens under those locks. The comment above `locked_with_legs` is rewritten with this full order.

### D33. Deleting entries of a posted period
Deleting an entry listed in a posted instance's `posted_entry_ids` deletes only that entry (and, as today, its children and its transfer pair) and removes it from the list. When entries remain, the instance stays `posted` with `is_partial = true` and `note = "部分入帳記錄已於 YYYY-MM-DD 刪除"`; the UI shows a 部分 badge and offers 重新入帳 (`repost`). When none remain: an instance with `acted_by = import` becomes `skipped` with `note = 入帳記錄已刪除` (MOZE booked it; it is never re-posted); any other becomes `pending` with `posted_entry_ids`, `acted_at`, `acted_by` cleared, `reopened_at = now()` and `note = "入帳記錄已於 YYYY-MM-DD 刪除"`. A reopened instance is never auto-posted (the owner deleted it on purpose); it waits in 待完成交易 with [入帳] [略過]. `POST …/instances/{id}/reopen` deletes all entries of a posted instance and makes it `pending` the same way, turns `skipped` back into `pending`, and sets an `ended` definition back to `active`. Whenever this path or `reopen` leaves a pending or partial instance on an `ended` definition, the definition becomes `active` again. `reopen` always ends `pending` (deleting every entry of the period, without the per-entry rules above) and is allowed even when the template references an archived row (posting then fails with `last_error`). `POST …/instances/{id}/accept-partial` (保留部分) clears `is_partial` and keeps `note`; partial periods are in 待完成交易 whatever their date, and count in the bell, until accepted or reposted. The importer's own full-replace delete never runs this logic; it recomputes import-posted instances itself (D37).

### D34. The daily job
`schedule_job.run(trigger)` with `trigger ∈ {cron, startup, retry, import, manual}`:
1. Take `pg_try_advisory_lock(SCHEDULE_JOB_LOCK_KEY = 0x53434844 /* "SCHD" */)` on a dedicated connection; when it is held the run returns `busy`. Released in `finally`.
2. Generate (D30), one transaction per definition, each taking the shared import key first.
3. Post: select ids of instances with `status = pending`, `due_date ≤ today`, `due_date ≥ definition.auto_post_from`, `reopened_at IS NULL`, definition `active` and `auto`, ordered by `definition_id, seq` — ★D31 wins (Multica R-F6): within one definition periods are attempted in `seq` order, never in `due_date` order, so a period the owner moved later is still attempted before the next one; post each (D31) in its own transaction with `acted_by = auto`: shared import key → the definition (`FOR SHARE`, `FOR UPDATE` with a loan line, as the post itself takes it) → the sequence barrier, checked under that definition lock: a period is not eligible while an earlier `seq` of the same definition is `pending` and either due for the job or failed (`last_error`), even when its `due_date` was moved past this one's (pre-`auto_post_from` and reopened periods are the owner's and do not hold the series) → the instance `FOR UPDATE SKIP LOCKED` (an instance the owner is acting on is left to the owner; to the barrier it still reads `pending`, so the later period waits for the next run). When the shared import key is not available the run stops with `import_running`. Within one definition a failure stops that definition's later instances for this run (a loan's periods must post in order), and the barrier keeps them waiting in later runs until the earlier period posts or is skipped; other definitions continue.
4. Return and log a report: `{trigger, today, status, generated, posted, failed, stopped_definitions}` — counts and ids only, no names or amounts.

Scheduling: APScheduler 3.11 `BackgroundScheduler(timezone="Asia/Taipei")` started from an `on_event("startup")` hook in `app/main.py` when `ACCOUNTING_SCHEDULER_ENABLED` is not false, with `CronTrigger(hour=0, minute=5)`, `coalesce=True`, `max_instances=1`, `misfire_grace_time=3600`; a one-off run 10 s after start; after a run that ended `busy` or `import_running`, a retry every 10 minutes until a run completes that Taipei day; and a run after every successful real (non-dry-run) backup import, fired once the import has released its advisory lock (trigger `import`). ★The standalone importer CLI has no scheduler, so `trigger_after_import` would do nothing there (Multica R-F4): after its import releases the lock, the CLI runs the job inline in its own process — generation always; posting only when `ACCOUNTING_SCHEDULER_ENABLED` is truthy (the scheduler's own parsing); otherwise the run logs the count of due but unposted instances. The API path keeps `trigger_after_import`. Stopped on shutdown. The advisory lock, not the in-process scheduler, guarantees a single runner, so a CLI run (`python -m app.services.schedule_job [--dry-run]`) or a second process is safe.

**No silent backlog** (owner decision): `auto_post_from` is the date a definition was created locally or first imported, so neither the first run after deploy nor a back-dated 起始日 auto-posts past periods. Pending instances due before `auto_post_from` appear in 待完成交易, where 補入帳至今天 posts them on the owner's tap. Before the first backup import on this schema there are no imported definitions, so the job has nothing imported to post.

### D35. Modes, pause, resume, end, catch-up, edit
- `auto` (自動入帳, default; MOZE 立即入帳) is posted by the job from `auto_post_from` on; switching a definition to `auto` with `PUT …/mode` sets `auto_post_from` to today, so a mode switch never posts a backlog; `confirm` (提醒入帳) never is: its due instances wait in 待完成交易 until [入帳] or [略過]. MOZE's 延後入帳 and 帳單折抵 are not offered.
- `pause` keeps pending instances and stops posting; paused definitions leave 待完成交易 and the bell and show 已暫停 in the 週期／分期 section. `resume` takes `backlog: skip | post` (default `skip`): pending instances due ≤ today are skipped (`acted_by = owner`) or, after the status change commits, posted one transaction each in seq order, stopping at the first failure. The default protects the owner from a burst of months they paused on purpose.
- `end` sets `ended` and deletes every `pending` instance (design doc §7); posted and skipped ones stay as history.
- `skip` (略過) never changes a loan's 剩餘: no entry is written, so the open amount stays; the prompt says `略過這一期？剩餘不變`. An `ended` loan definition whose loan still has a non-zero open amount shows 需檢查.
- `catch-up` (補入帳至今天) posts every pending instance of the definition due ≤ today in seq order, whatever the mode, `auto_post_from` or `reopened_at`, one transaction each, stopping at the first failure; refused with 409 while the definition is `paused`.
- `PUT` (編輯整個排程) replaces name, template, interval, anchor, `day_of_month`, `times`, `end_date`, `total_amount` (not `kind`), deletes `pending` instances due on or after tomorrow, and regenerates: the first new instance is the new rule's first occurrence on or after tomorrow and strictly after the latest remaining instance's `due_date`, with `seq` = the remaining maximum + 1, inserted by the edit itself, after which generation (D30) continues strictly after its `rule_date`. ★Occurrences are always computed from the rule anchor (Multica R-F3): the edit never rebases `anchor_date` or `first_seq` implicitly — rebasing a Jan-31 rule on Feb-1 to Feb-28 would give Mar-28 next, and a Feb-29 yearly rule rebased into a common year would never return to Feb-29. The anchor changes only when the owner sends a different `anchor_date` (stored as occurrence 0 of the new rule); then a `month` / `year` rule sent without `day_of_month` gets `day_of_month` = the new anchor's day. With the anchor unchanged, `day_of_month` is stored as sent (NULL keeps the anchor's own day). Overrides of the remaining (overdue) pending instances are realigned to the new lines: kept for a line still at the same index with the same kind, else cleared. Posted and skipped instances are untouched.
- `PUT …/instances/{id}` (編輯這一筆 on a pending period) sets `due_date` and / or `amounts` and `edited_by_owner = true`; a `due_date` equal to a posted instance's date of the same definition is refused (422). `POST …/instances/{id}/repost` (編輯這一筆 on a posted or partial period; refused with 409 `locked_until_cutover` before cutover for an `acted_by = import` period, whose sheet shows the lock banner) deletes its entries and posts again with new amounts in one transaction, so a repayment, which `PUT /entries` refuses (`is_settlement`), can still be corrected.
- ★Amount edit scope (owner decision 2026-10-04, proposal decision 24): `PUT …/instances/{id}` takes `scope` — `this` (default, 僅這一期: the behaviour above), `following` (這一期與之後) or `all` (全部週期). The SPA asks `套用範圍` after the owner changes an amount of a pending period. `following` / `all` accept `amounts` only (any other field, or no `amounts`, → 422 naming `scope`; each amount > 0, since they become template amounts) and run in one transaction under key → definition `FOR UPDATE` → every instance `FOR UPDATE` ascending id: `following` first gives every earlier pending instance without an override the current template amounts as its override (it keeps the old price); then both set the template's line amounts to the new ones with `template_owner_edited = true` and clear the override of every pending instance from this one on (`following`) or of every pending instance (`all`) unless it is owner-edited; this instance follows the template, or, when it was already owner-edited, takes the new amounts as its override. Posted and skipped instances never change. ★An installment with a total keeps its total against the ACTUAL allocations (Multica R-A1): its pending last period gets `[residual, …]` with residual = total − Σ of the first line's effective amount of every other period (posted as posted — its override, else the template before the edit; skipped excluded; pending after the edit — preserved owner overrides, the old price `following` keeps, imported amounts, else the new template; not yet generated — the new template), for local and imported definitions alike; a residual ≤ 0 is refused (422 `amounts`, message without amounts) and nothing changes. `schedule_generation.last_period_override` is not used for scoped edits; it stays for the generation path, so a last period generated later (a loan longer than the 13-month horizon) takes `total − amount × (times − 1)`. Example: 10,000 over 3 (3,333 / 3,333 / 3,334), 這一期與之後 from the second at 3,000 → 3,333 / 3,000 / 3,667. Amounts are not rule fields, so imported definitions accept these edits before cutover (D36's lock still refuses `PUT` / `DELETE` of the definition). This replaces the earlier open owner choice between MOZE's earliest and latest record amount for HomeHub-generated periods: the import keeps the earliest record (below), and the owner fixes a price with 這一期與之後 or 全部週期.
- `DELETE` is refused (409) while the definition has posted instances; the owner ends it instead.

### D36. Mirror period: imported schedules post too, and the importer reconciles
Until cutover the owner still uses MOZE, which books the same periods. HomeHub posts imported definitions (from their `auto_post_from` on) and the importer reconciles (D37): a past MOZE record that a HomeHub posting (or skip) already covers is not imported again. Consequences:
- Posting a repayment against an imported (`moze_backup`) payable bypasses D19's lock on the **target** only; the new row is a `schedule` row, which imports never delete. The importer re-points such settlements to the re-created payable (D37).
- Template **edits** (`PUT`, `DELETE`) of an imported definition are refused with 409 `locked_until_cutover` before cutover, because the next import would overwrite them; `pause`, `resume`, `end`, mode changes and instance actions are allowed, and the importer keeps `status` and `posting_mode` (they are the owner's).

### D37. Import mapping and re-import
- **Installments.** `AHInstallment` → `installment`: `interval = month × 1`, `day_of_month = dayOfMonth`, `anchor_date = dateInfo[0]` (★ruling R2: MOZE leaves `dateInfo` empty, so the dates are the record groups' once the origin — a loan's type-4 pair, or the purchase record sharing the first period's date — is set aside; see Implementation notes), `times`, `total_amount = total`, `first_seq = 1`; lines from the shape of its first package (repayment → `repayment` line with `loan_entry_id` = the entry imported from the first repayment's `relatedID`, `account_id` = the record's account, `category_id`, `amount = |price|`; its packaged type-15 record → an `interest` line; a type-0 installment → an `expense` line); `name` = the first record's `name`, else its category's name, else `分期`. `dateInfo` that is not monthly on `dayOfMonth` (clamped) gives `review_reason = interval_mismatch`.
- **Recurring.** `AHPeriod` → `recurring` by the map confirmed on all 11 rows of the real backup: `unit` 1 → `week` (the weekday is `days`; `day_of_month` NULL), `unit` 2 → `month` with `day_of_month = days` (clamped, D30); `interval_n = 1` (`count` = 1 everywhere); `times` 0 → NULL (unlimited), else `times` (★Task 28 ruling R3: the single disabled extra group MOZE keeps in a finite series is dropped as an artifact, see Implementation notes); `anchor_date` = the date of the **earliest** record generated for that `eventID` (past or future), `first_seq = 1` there, because `startDate` is the next occurrence MOZE tracks, not the first — `startDate` only confirms the phase (★ruling R4: only its phase is checked — the rule's clamped day of month, or its weekday — and it may lie before or after the anchor); lines from the first generated record (`type` 1 → a `transfer` line from the transfer pair, `type` 0 → the record's own kind). Any other `unit`, a weekday that disagrees with the anchor, or a `startDate` off the rule imports the definition `paused` with `review_reason = interval_mismatch`.
- **Single future records.** A future record without `eventID` (other than a reward) → its own `recurring` definition with `times = 1` and `moze_id = "record:" + identifier`.
- **Defaults.** `posting_mode = auto` (MOZE's default 立即入帳; a MOZE posting-mode field, if one is found, maps 提醒入帳 → `confirm`); `auto_post_from` = the import's Taipei date; a missing loan record gives `review_reason = loan_missing` and `paused`.
- **Instances and seq.** Each non-reward record (past with an `eventID`, or future) → an instance of its definition with `moze_id` = the record id and `due_date` = its date (Taipei). `seq`: for an `AHInstallment`, the 1-based position of that date in `dateInfo`; for an `AHPeriod`, 1 + the occurrence index of that date counted from the anchor (the earliest generated record) over past and future records together. `amount_override` = `|total|` per line (fee and bonus folded, as MOZE's `total`), `"0"` for a line whose package member is missing. A type-15 record sharing a `packageID` with a repayment, and the in-leg of a transfer, merge into the same instance (`moze_record_ids`). Two records of one definition on the same date are reported under `schedules.review` and only the first is mapped.
- **Past, disabled and future.** Past records already imported as entries → `posted` instances with `acted_by = import`, `acted_at` = the import's start time, `posted_entry_ids` = those entries. Disabled records with an `eventID` (past or future) → `skipped` instances with `acted_by = import`. Enabled future records → `pending`.
- **Re-import** (in the importer's ledger transaction, after locking the schedule rows it touches, D32): definitions are upserted by `moze_id` (rule and template refreshed; `posting_mode`, `auto_post_from` kept; `status` stays as the owner left it, except that a mismatch or `loan_missing` new in this import sets `review_reason` and pauses, and a resolved `review_reason` is cleared without changing `status`). Instances are upserted by `moze_id`; an instance without `moze_id` (HomeHub-generated beyond MOZE's horizon) of the same definition whose `rule_date` (else `due_date`) equals the record's date is **adopted**: it gets the record's `moze_id` and `moze_record_ids`, and, when pending and not owner-edited, its `amount_override`; a `posted` one keeps its entries and the record counts as `past_records_already_posted`. A record whose computed `seq` belongs to another instance is listed under `schedules.review` and skipped; the existing seq is kept and the import never fails on it. `pending` imported instances are refreshed unless `edited_by_owner`; ★an owner-edited pending instance whose MOZE record is now past keeps the owner's pending choice (Multica R-F1): the record is suppressed (not imported as an entry, so the period is never both imported and independently postable), the instance stays `pending` with its override, the report lists it under `past_records_owner_pending` (`definition_id`, `seq`, `date`), the balance comparison adds the suppressed record's MOZE amount to `moze_part`, and a later post writes the period once (the next import then counts the record as `past_records_already_posted`); `acted_by = import` instances are recomputed from the newly imported entries (one with no entries left becomes `skipped`, `acted_by = import`); instances `posted` by `auto` / `owner`, every `skipped` instance whose `acted_by` is not `import`, and owner-edited pending instances are kept unchanged. A past MOZE record whose id is in a kept posted or skipped instance's `moze_record_ids` is **not** imported as an entry (counted `past_records_already_posted` / `past_records_already_skipped`; ★each line HomeHub posted is compared with the matching MOZE record — repayment, interest, expense, both transfer legs; `moze_record_ids` keeps which record is which line — never period totals (Multica R-F5), and each differing line is listed under `past_records_amount_differs.lines` as `{definition_id, name, seq, date, line, kind, amount, moze_amount}` beside the instance `count` / `instance_ids`; owner-facing like `loan_remainder_check`, never logged), and the balance comparison counts that instance's `schedule` entries in `moze_part` instead. Imported pending instances absent from the backup are deleted; HomeHub-generated pending instances (no `moze_id`) are never deleted by an import. An imported definition absent from the backup is `ended` (pending deleted) when it has posted or skipped instances, else deleted. No pending instance is created for an `ended` definition. `created_locally` definitions and their instances are never written by an import, except the link re-pointing below.
- **Re-pointing.** Entries are fully replaced on import (D13), so ids of MOZE entries change. Before deleting (and after locking the schedule rows), the importer maps every `loan_entry_id` in any template and every `settles_entry_id` of a `schedule` entry that points at a MOZE entry to that entry's `moze_id`; after inserting it re-points them to the new ids. A target that disappeared clears the link and pauses the definition with `review_reason = loan_missing`.
- ★**Owner-set template amounts.** A definition with `template_owner_edited = true` (D35 amount edit scope) keeps its template's line amounts on re-import (a refreshed line at the same index with the same kind keeps the stored amount); MOZE's per-period amounts are not written as `amount_override` on its pending instances (new, refreshed or adopted), and each line of a pending period whose MOZE amount differs is listed in the report under `amount_differs` (per line, the same item shape as `past_records_amount_differs.lines` — an owner-facing list with amounts, like `loan_remainder_check`; never logged). ★The same comparison runs for every retained `edited_by_owner` pending period, at the amounts it will post (its override, else the template; Multica R-A2). The SPA's import report shows both lists as a count plus one line per item (definition name, 第 k 期, date, HomeHub vs MOZE amount; Multica R-A3). Adoption, dates and statuses follow the rules above.
- **Facts the report checks** on the real backup: 11 + 14 definitions, 534 records mapped, 63 rewards ignored (534 + 63 = 597), and per loan definition `remainder` (MOZE's remaining principal) against the payable's open amount after import.

### D38. Loans: 剩餘, 已還, 下期
A definition is a **loan definition** when a line is `repayment` (or `collection`). A loan created in the form sets `total_amount = loan.amount`; the per-period repayment is `floor(total ÷ times)` in whole units and the last period's override covers every line (e.g. `["8345", "620"]`) and its repayment is clamped to the loan's remaining open amount (D31), e.g. 300,000 over 36 → 8,333 × 35 and 8,345 last. Its `remaining` is the loan entry's `open_amount` (0 when `is_closed`), signed like the original (`−` for a payable). `repaid` is `Σ |amount|` of every settlement of the loan (from schedules or by hand). `next_due_date` / `next_amount` are the earliest pending instance's. For a non-loan installment (MOZE's card 分期, whose unposted remainder MOZE keeps in the 分期帳款 system account), `remaining = total_amount − Σ |amount|` of the entries actually posted for its first line (read through `posted_entry_ids`); HomeHub does not post to a system account — the imported 分期帳款 account stays archived and out of the total (2a) and the definition row shows the remainder instead.

Downgrade refuses (naming counts) while any `schedule` entry exists or any instance has `acted_by` `auto` / `owner`; otherwise it deletes the definitions and instances, drops the tables and enums, recreates `moze_schedule` empty (the next 2a import refills it), and shrinks `entry_source` with the `_shrink_enum` pattern of `7b1e4a2c9d05`.

Under `/api/accounting/schedules` (spec "Definition endpoints", "Definition state endpoints", "Instance endpoints", "Run-now endpoint"): definitions list / get / create / update / delete, `pause`, `resume`, `end`, `mode`, `catch-up`; instances list / edit / `post` / `skip` / `reopen` / `repost` / `accept-partial`; `run-now`. ### D41. Timezone
Every date is a naive Asia/Taipei date: `due_date`, `anchor_date`, `end_date`, `auto_post_from`, `generated_until`, "today" (`ledger_service._today()`), the horizon and `overdue_days`. Timestamps (`acted_at`, `last_error_at`, `reopened_at`) are TIMESTAMPTZ. The cron trigger is in Asia/Taipei; the host's zone does not matter.

### D42. Security
No new auth surface: the schedule endpoints, including `run-now`, sit behind the same perimeter as every accounting endpoint (Tailscale-only Caddy) and behind the optional bearer-token auth of #42. `app/auth.py` `ApiTokenMiddleware` is installed app-wide: when `ACCOUNTING_API_TOKENS` is set, every request except `GET`/`HEAD` on `/health` and `/health/ready` (and the docs pages when `ACCOUNTING_DOCS_PUBLIC=true`) needs `Authorization: Bearer <token>`, else 401; unset, it is a pass-through. The new `/schedules/*` routes (reads and writes, `run-now` included) are covered by that middleware with no extra code; the SPA's `accounting-token.interceptor.ts` already adds `ACCOUNTING_SPA_TOKEN` to every `/api/accounting` call. Operator `curl`s, verify steps and the preview verify server must pass the token when it is set. `run-now` is guarded by the advisory locks and per-instance status, so a repeated call cannot double-post. Logs carry ids, counts and error classes, never names, amounts or counterparties.

## Risks / Trade-offs

- **[Double posting during the mirror period]** → D37 skips a past MOZE record that a HomeHub posting already covers, matched by record id, and the report counts it (and amount differences); posting is idempotent by row lock + status + the partial unique index. Residual risk: the owner posts a period in MOZE under a different record (deleting MOZE's generated one); the importer then imports both and the report cannot know. The owner checklist includes one loan month.
- **[`AHPeriod` rule drifts in a later backup]** → the map was confirmed on all 11 rows; the importer still checks every definition's records against its rule and imports a mismatch paused (`interval_mismatch`), never silently wrong.
- **[Job does not run]** (pm2 down at 00:05) → startup run, 10-minute retries, a run after each import, and the 補入帳至今天 / run-now buttons; `coalesce` prevents a burst of runs.
- **[A long-failing loan blocks later periods]** → by design (order matters); the failure shows on the definition row and in 待完成交易 with a retry, and the owner can skip the period.
- **[Import vs schedule writes]** → the shared/exclusive advisory key plus the importer locking schedule rows before its deletes; schedule writes answer 409 `import_running` for the few seconds an import runs.
- **[Lock-order regression]** → the order is written once (comment above `locked_with_legs`, extended) and tested with two threads (post vs delete of its entry, edit vs post, import vs post).
- **[Owner deletes an auto-posted entry and expects it gone]** → D33 keeps the period pending (or partial) but never auto-posts it again; it waits in 待完成交易 for 略過.
- **[Interest varies per period]** → imported periods carry MOZE's amounts in `amount_override`; new local loans use a flat interest until Phase B.
